# Безопасность

Rivet запускает coding-агентов, которые выполняют команды на машинах
runner'ов, и хранит токены хостингов кода и ключи моделей. Дыры в нём
дороже обычного. Спасибо, что сообщаете о них приватно.

*English: please report vulnerabilities privately through GitHub Security
Advisories of this repository (Security → Report a vulnerability). Do not
open public issues for security problems. Read the runner threat model below
before you run runners on a machine with anything valuable on it.*

## Как сообщить

Только приватным отчётом через **GitHub Security Advisories** этого
репозитория: вкладка **Security → Report a vulnerability**. Отчёт видят
только сопровождающие проекта. В том же обсуждении договариваемся об
исправлении и о публикации. Дыры в консоли, e2e и мобильных клиентах
сообщайте сюда же или в одноимённый раздел их репозитория.

Не открывайте issue, PR или обсуждение с описанием дыры, пока она не
исправлена.

Что приложить:

- версию: она видна в ссылке «Исходный код · версия» на странице входа
  консоли и в ответе `GET /api/v1/about`
- как воспроизвести и что получает нападающий
- только выдуманные данные: токены, ключи, адреса и репозитории замените.

Получение отчёта подтверждается в обсуждении advisory. После исправления
advisory публикуется с описанием и, если хотите, с благодарностью вам.

## Какие версии поддерживаются

Исправления выходят для последнего релиза и ветки `main`. Старые версии
отдельно не исправляются, обновляйтесь.

## Модель угроз runner'а

Прочитайте это до того, как запускать runner.

**Что делает агент.** Runner ведёт агентский цикл Rivet: модель получает
задачу и инструменты, в том числе `run`, который выполняет команды в
рабочей копии, а проверки проекта (`go test`, `npm test` и подобные)
исполняют код из ветки задачи. Модели вы не доверяете полностью: её
ответы формирует в том числе содержимое репозитория, задач и интервью,
куда может попасть чужой текст. Поэтому считайте, что команды агента и
проверки выполняет недоверенный код.

**Песочница (Linux).** На Linux с непривилегированными user namespaces
команды агента и проверки идут в песочнице: свои user, mount, net и pid
namespace, сети нет (кроме собственного loopback), окружение из белого
списка, домашний каталог runner'а и файл токена скрыты, кеши зависимостей
доступны только на чтение. Это рабочий режим для production. Флаг
`-checks-network` возвращает сеть хоста проверкам проекта (не командам
агента), `-sandbox-ro` открывает каталог на чтение. Оба флага осознанно
расширяют то, что видит код из ветки задачи.

**Без песочницы (`-unsandboxed`).** На macOS, на Linux без user namespaces
и в Docker с профилем seccomp по умолчанию песочницы нет. Тогда runner с
агентом не стартует, пока администратор явно не укажет `-unsandboxed`
(`RIVET_RUNNER_UNSANDBOXED=1`). С этим флагом команды агента и проверки
выполняются **со всеми правами пользователя ОС, под которым запущен
runner**: читают и меняют его файлы (в том числе файл токена регистрации,
ключи подключений, SSH-ключи и облачные учётные данные в `$HOME`), ходят в
сеть и во внутренние сервисы, запускают фоновые процессы. Runner пишет
предупреждение в журнал, консоль помечает его «команды агента с доступом в
сеть». Этот режим годится для доверенной модели и отладки, не для
production.

**Секреты runner'а.**

- Токен регистрации передавайте файлом с правами `0600` в
  `RIVET_RUNNER_TOKEN_FILE`. Файл с доступом для группы или остальных
  runner не принимает. Флаг `-token` устарел: значение видно в списке
  процессов.
- Токен и ключи, пришедшие переменными окружения, runner при старте
  забирает в память и перезапускает себя с очищенным окружением, поэтому
  они не видны в `ps eww` и `/proc/<pid>/environ` и не наследуются
  командами агента, проверками и командами выкатки.
- На Linux процесс runner'а помечен недампируемым (`PR_SET_DUMPABLE=0`):
  процессы того же пользователя не читают его память и окружение. На macOS
  аналога нет.
- Всё это **не защищает файлы на диске** от команды под тем же
  пользователем. Файл токена и ключи закрывает только песочница или
  отдельный пользователь, у которого нет других секретов.

**Как запускать runner.** Под отдельным пользователем ОС без чужих
секретов, а лучше в отдельном контейнере или виртуальной машине на каждый
runner. Не запускайте runner под своей учётной записью с SSH-ключами,
токенами облаков и доступом к рабочим сетям. Токен хостинга, который
получает runner, давайте с минимальными правами на нужные репозитории.

## Control plane (rivetd)

- **Адреса.** По умолчанию rivetd слушает только loopback
  (`127.0.0.1:8080` для API и консоли, `127.0.0.1:8090` для протокола
  runner'ов). Наружу открывайте явно, API за TLS-прокси
  (`RIVET_TRUST_PROXY=1`), протокол runner'ов с TLS
  (`RIVET_GRPC_TLS_CERT`, `RIVET_GRPC_TLS_KEY`), а лучше и с клиентскими
  сертификатами runner'ов (`RIVET_GRPC_CLIENT_CA`, mTLS). Без TLS вне
  loopback rivetd пишет предупреждение: токены runner'ов и секреты
  назначений идут открытым текстом. Токен регистрации привязан к
  идентификаторам runner'ов: по чужому токену другой runner не
  зарегистрируется.
- **Ключ шифрования.** Токены хостингов, ключи и секретные заголовки
  подключений к моделям хранятся в базе зашифрованными AES-256-GCM ключом
  `RIVET_SECRET_KEY`. Ключа в базе нет, и по дампу базы эти секреты не
  расшифровать. Храните ключ отдельно от резервных копий. Сменить ключ:
  `rivetd -rotate-key` (README, «Смена ключа шифрования»).
- **Что в базе открытым текстом.** Секреты подписи webhook'ов проектов
  (`projects.webhook_secret`) хранятся без шифрования: тот, у кого есть
  дамп базы, может подделывать webhook'и этих проектов. Дамп базы
  защищайте как секрет, а после его утечки считайте секреты webhook'ов
  раскрытыми.
- **Опубликованные значения.** rivetd не стартует с ключом шифрования из
  документации и примеров и с таким же паролем первого администратора.
  Администратора, у которого в базе остался такой пароль, rivetd при
  следующем входе заставляет сменить пароль. `docker-compose.yml` своих
  значений не подставляет.
- **Доступ.** API закрыт сессией или personal access token, webhook'и
  проверяются подписью хостинга, токены runner'ов и PAT хранятся хэшем.

## Что считается уязвимостью

Например:

- выход команды агента или проверки из песочницы, чтение файла токена,
  `$HOME` runner'а или сети, когда песочница работает
- секрет одного проекта или установки (токен хостинга, ключ модели, токен
  runner'а) попадает в рабочую копию, транскрипт, журнал, событие, ответ API
  или в другой проект
- вход без пароля и токена, обход ролей и видимости проектов,
  изменение чужого проекта
- обход политик: merge без review там, где он требуется, публикация без
  разрешения, назначение задачи runner'у вне правил
- webhook без верной подписи меняет состояние задачи
- проверка URL control plane'ом уходит во внутреннюю сеть, закрытую
  политикой установки
- код из рабочей копии выполняется git'ом runner'а (хуки, фильтры,
  `core.fsmonitor` и подобное).

Не уязвимость то, что администратор разрешил сам: `-unsandboxed`,
`-checks-network`, `-sandbox-ro`, `RIVET_ALLOW_PRIVATE_URLS`, протокол
runner'ов без TLS вне loopback после предупреждения. Не уязвимость и атака,
для которой уже нужен доступ к базе вместе с ключом шифрования или права
пользователя ОС, под которым работает rivetd или runner.
