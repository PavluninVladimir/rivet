# Проектный ассистент

Ассистент объясняет состояние проекта и выполняет `task.retry`, `epic.resume`, `environment.resume`. Модель возвращает диагноз и намерения в JSON. Доступа к shell, SQL, браузеру, произвольным инструментам, merge, публикации, отмене, пинам и редактированию модели у неё нет.

## Включение

Миграция `1001_project_assistant.sql` добавляет отдельные таблицы конфигурации, диалога, запусков, действий, lease, эпизодов retry и отложенных событий. Существующие задачи и публикации не переписываются.

По умолчанию автоматический режим выключен, подключение и модель не выбраны. Владелец проекта выбирает существующую модель каталога и задаёт пределы через `PATCH /api/v1/projects/{id}/assistant/config`. Проектный владелец не обязан быть администратором установки. Список моделей доступен через `/api/v1/models/choices`.

Сохранение конфигурации использует `expected_revision`. Владелец, сохранивший её, становится sponsor автоматического режима. Вопросы и восстановление по явному запросу действуют с правами инициатора. Обработка событий дополнительно требует включённого режима и актуальных прав владельца у sponsor.

Пределы по умолчанию: три действия, 120 секунд на запуск, 32 000 входных и 4 000 выходных токенов, 100 000 токенов в сутки. До вызова резервируется полный настроенный вход и выход. Для проверки размера входа используется консервативная оценка по UTF-8 байтам. Большой снимок отклоняется до вызова, а не обрезается незаметно. Неизвестная цена допустима при token cap, но запрещает вызов с обязательным денежным cap. Встроенных повторов запроса модели нет. Реальные платные проверки модели при реализации не запускались.

## Проверки действия

Непосредственно внутри транзакции доменного перехода проверяются действующий пользователь, членство, sponsor для event-режима, версия конфигурации, lease и fencing epoch, отсутствие stop, лимит действий, решение policy engine и версия ресурса. Политика не выдаёт отсутствующих по коду прав. Неизвестный/отсутствующий движок блокирует изменение.

Исполнение использует существующие `ResolveTask`, `TransitionEpic` и `SetEnvPaused`. Смена состояния, штатное событие и успешный результат действия ассистента фиксируются одной транзакцией. Повтор с тем же operation ID читает сохранённый успех. Retry означает возвращение в очередь, а не завершение задачи. Счётчик попыток сбрасывается только по существующей семантике `ResolveTask`, лимит попыток не увеличивается.

Новая сессия, timestamp, status transition или сброшенный counter не создают новый failure episode. Текущая версия консервативно объединяет неразрешённые сбои одного шага на неизменных причинных входах. Проверяемая смена описания, снимка процесса или привязки модели образует новое основание. Восстановление ресурсов без надёжно установленной причинной связи само по себе не разрешает второй retry.

Если требуется удалённое создание PR перед review, автоматический retry направляет к штатной операции пользователя. Удалённая подготовка PR пока не имеет необходимого для этого реестра идемпотентного контракта. Ассистент не запускает её в обход проверки.

## События и наблюдение

Durable feed читает журнал событий небольшими партиями. Только изменения failed/blocked задачи, paused Epic и paused окружения могут планировать анализ. Одинаковая причина и revision дедуплицируются. Изменения одного проекта собираются в течение 30 секунд, после чего создаётся свежий снимок. Неудачная постановка отложена на 60 секунд. Heartbeat и обычный reconcile не вызывают модель.

Снимок читает данные в repeatable-read транзакции: задачи и зависимости, Epic, нерешённые attention, инциденты, окружения, последние локальные публикации, исследования, сессии без транскриптов, доступность runner и моделей. Конфигурации окружений, пароли, ключи, HTTP-заголовки и полные логи в модель не передаются. Сервер формирует ссылки и проверяет возвращённые моделью evidence IDs. Диагноз модели не заменяет факты снимка и журнал подтверждённых действий.

Снимок ограничен 500 Epic, 1 000 задачами, 200 attention, 100 инцидентами, 100 окружениями, 100 последними сессиями, 200 runner и 100 подключениями. Крупным проектам может понадобиться отдельное разбиение контекста. Running публикация не подтверждает бизнес-приёмку. Неизвестные результаты старого исследования не становятся автоматически `backlog_ready`.

События `assistant.*` служат invalidation. История и результаты перечитываются через REST после reconnect. Действия также сохраняют обычные доменные события для Tasks/Overview. Старые DEPLOY_FAILED не скрываются ассистентом; их восстановление относится к отдельной проверке публикации.

## Остановка и восстановление

Stop запрещает новые действия и новые вызовы модели, сохраняя уже выполняющийся запрос и его расход. Проектные задачи, runner и публикации не отменяются. Stop и сообщения требуют `Idempotency-Key`; иное тело с тем же ключом даёт конфликт.

Lease на проект исключает двух одновременных исполнителей. Если процесс перезапущен во время обращения к модели, запуск после истечения lease завершается консервативно. Модель не вызывается повторно автоматически: её приём и стоимость могли остаться неизвестными. Успешные доменные эффекты сохраняются в той же транзакции, что их action result, поэтому восстановление не повторяет их.

## Проверка и откат

`go test ./internal/assistant ./internal/store ./internal/api -run '^TestAssistant' -count=1` выполняет unit, реальные изолированные PostgreSQL и HTTP fake-model проверки. Есть сценарии ACL/revocation, CAS, replay, конкурентного lease, fenced executor, одного retry на причину, stop, денежного/token budget, debounce и трёх typed actions. Отдельный API-сценарий проверяет, что вопрос не меняет задачу, а recover действительно возвращает failed задачу в queued.

Перед выкаткой нужны общие проверки backend/web/e2e, независимое security/code review, резервная копия базы и безопасное окно обновления control plane. Обновление не следует прерывать активные coding/fix сессии. Сначала интегрируется backend, затем web и e2e по установленному процессу проекта.

Для функционального отката владелец выключает автоматический режим и останавливает активный run. Для полного отключения новых запросов убирается запуск `RunAssistant` или откатывается бинарник. Таблицы и история сохраняются, additive migration обратно не удаляется. Завершённые действия проекта не откатываются автоматически. Совместимость старого API сохраняется, mobile-клиент не обязан добавлять новый экран.
