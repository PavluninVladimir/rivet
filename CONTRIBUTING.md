# Как участвовать

Спасибо, что хотите помочь Rivet. Здесь порядок, проверки и правила, без
которых правку не примут. Устройство проекта и сборка описаны в
[README.md](README.md).

*English speakers: issues and pull requests in English are welcome, but the
project language is Russian: comments, UI strings, log messages and
specifications stay in Russian. Contributions require signing the
[CLA](CLA.md).*

Правила общие для всех репозиториев проекта: `rivet` (этот, Go-бэкенд),
[rivet-web](https://github.com/PavluninVladimir/rivet-web) (консоль),
[rivet-e2e](https://github.com/PavluninVladimir/rivet-e2e) (сквозные
тесты), `rivet-android` и `rivet-ios`.

## Язык и имена

- Язык проекта русский: комментарии, тексты интерфейса, журнал, сообщения
  об ошибках, спеки и описания изменений. Строка, которую увидит человек,
  пишется по-русски.
- Имена в коде латиницей, общепринятыми английскими словами. Не
  транслитерируйте.
- Пишите просто, без канцелярита. Короткие предложения лучше длинных.

## Прежде чем писать код

- **Небольшая правка** (ошибка, опечатка, тест) сразу идёт PR.
- **Изменение поведения** начинается с требований. Rivet разрабатывается
  по OpenSpec: у изменения есть предложение, дизайн, дельта спек и список
  задач, и его обсуждают до кода. Пока спеки не перенесены в репозиторий,
  откройте issue с описанием того, что и зачем хотите изменить.
- **Заметная правка консоли** сверяется с дизайн-прототипом: тёмная тема,
  цветовые токены в oklch, без новых экранов сверх спеки.
- Сомневаетесь, откройте issue.

## Главный принцип

Модель решает задачу, Rivet управляет процессом. Переходы между этапами,
проверки, повторы, зависимости и блокировки держит детерминированный код, а
не промпт. Правка, которая переносит логику процесса в текст для модели,
не принимается.

## Правила проекта

- **Смена статуса и событие пишутся одной транзакцией.** Прямых `UPDATE`
  статусов в обход переходов хранилища быть не должно. Каждое действие
  оставляет событие в журнале.
- **Миграции применяются по имени**, порядок важен. Новая миграция берёт
  следующий свободный номер.
- **Секреты не попадают в журнал, транскрипт, событие и ответ API** ни в
  каком виде. Новый вид шифрованного секрета добавляется в перешифровку
  `rivetd -rotate-key` (`internal/store/rotate.go`).
- **Безопасные умолчания.** Новая настройка по умолчанию закрывает доступ,
  а не открывает его. Пароль администратора или ключ шифрования,
  появившийся в документации, примере или скрипте стенда, сразу вносится в
  список опубликованных значений (`internal/config/published.go`), тест это
  проверяет. Стенды генерируют свои значения при запуске.
- **Недоверенные данные разбираются осторожно.** Новый разборщик входа
  извне (webhook, ответ модели, файл из репозитория) покрывается
  fuzz-тестом, цель добавляется в `FUZZ_TARGETS` в `rivet-service/Makefile`.
- **Тестовые данные только выдуманные:** логины `alice` и `bob`, адреса
  `example.com` и `example.org`, токены заведомо фальшивые
  (`ghp_Example…`). Ни настоящих адресов, ни имён, ни ключей.
- **Зависимости только с совместимой лицензией** (MIT, BSD, ISC,
  Apache-2.0 и подобные). Новая зависимость обновляет `NOTICE` и
  `THIRD_PARTY`: `make third-party` в `rivet-service`.

## Проверки перед PR

Из `rivet-service/` (тестам хранилища нужен Postgres, например
`docker compose up -d postgres` с `.env` из `.env.example`):

```sh
go build ./...
go vet ./...
RIVET_DATABASE_URL='postgres://rivet:rivet@localhost:5432/rivet?sslmode=disable' go test ./...
golangci-lint run ./...
make fuzz FUZZ_TIME=15s     # если трогали разборщики
```

Правили протокол runner'ов: `make proto`. Правили консоль: в `rivet-web`
`npx tsc -b`, `npm test`, `npm run build`. Поведение, видимое в браузере,
проверяется сквозными сценариями `rivet-e2e` (ветка с тем же именем во всех
затронутых репозиториях, CI e2e берёт одноимённые ветки).

Тесты не заменяют проверку на живом стенде. Напишите в PR, как проверяли.

## Ветки, коммиты и PR

- Ветки по GitHub Flow: `feature/<имя>` или `fix/<имя>` от `main`, слияние
  через PR после зелёного CI. Прямых коммитов в `main` нет.
- Один PR, одна мысль. Рефакторинг и исправление логики разделяйте.
- Сообщение коммита по-русски, о работе: что изменилось и почему.
- **Без подписей помощников и машинных трейлеров**: ни строк соавторства от
  инструментов, ни идентификаторов сессий, ни «сгенерировано тем-то».
  Сообщение говорит о работе, а не о том, кто держал клавиатуру. Ваше
  авторство остаётся в поле автора коммита.

## Соглашение участника (CLA)

Чужие правки принимаются только с подписанным [CLA](CLA.md). Подпись
ставится один раз на человека через CLA Assistant: бот попросит её в первом
же PR, и без неё PR не сливается. Правки владельца проекта CLA не требуют.

**Зачем это нужно.** Rivet распространяется под AGPL-3.0-only, а владелец
проекта оставляет за собой возможность продавать коммерческую лицензию тем,
кому AGPL не подходит (двойное лицензирование). Для этого у него должно
быть право выпускать под другой лицензией весь код, в том числе ваш вклад.

**Что вы отдаёте и что остаётся у вас.** CLA это лицензия, а не передача
прав, по образцу Apache ICLA:

- авторские права на ваш вклад остаются у вас, вы можете использовать его
  как угодно, в том числе в других проектах
- владелец проекта получает бессрочную, безотзывную, неисключительную и
  бесплатную лицензию на ваш вклад с правом сублицензировать и
  перелицензировать его
- то, что уже опубликовано под AGPL, под AGPL и остаётся: коммерческая
  лицензия появляется рядом с открытой, а не вместо неё.

DCO (подпись `Signed-off-by`) не используется: она подтверждает только
право отдать код под лицензией проекта и перелицензирования не даёт.

## Лицензия вклада

Ваш вклад входит в проект под AGPL-3.0-only с дополнительным разрешением по
разделу 7 ([LICENSE-EXCEPTION](LICENSE-EXCEPTION)). Правки протокола
runner'ов (`rivet-service/pkg/protocol`) выходят под Apache-2.0, правки
встроенных модулей политик (`rivet-service/internal/policy/rego`),
предустановленных профилей агентов и шаблонов ролей дополнительно под CC0
1.0, как и они сами.

## Безопасность

Об уязвимостях не пишите в issues и PR, только приватным отчётом, как
описано в [SECURITY.md](SECURITY.md).
