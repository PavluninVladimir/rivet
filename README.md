# Rivet

Rivet is an orchestrator for autonomous software development with AI coding
agents. Its built-in agent runs on the model provider of your choice
(DeepSeek, OpenAI, Anthropic, OpenRouter, or a local Ollama or LM Studio
server). A human sets an Epic and approves the plan; Rivet splits it into tasks, builds a dependency graph,
runs the tasks on connected runners, gets them tested and reviewed by an
independent agent, and merges the result. People are pulled in only where a
real decision is needed. This repository holds the Go backend
(`rivet-service`); the web console, end-to-end tests and mobile clients live
in separate repositories listed below. Documentation is in Russian.

Rivet — оркестратор автономной разработки: control plane для команды из
coding-агентов. Человек ставит Epic, проверяет план и запускает выполнение.
Дальше процессом управляет Rivet, а человека зовёт только туда, где нужно
решение: задача заблокирована, исчерпаны попытки, не хватает информации,
автопроверка не дала вердикта.

Конвейер: **Epic → Tasks → DAG → Coding → Tests → Review → Fix → Merge →
Done**. Rivet декомпозирует Epic на небольшие задачи, находит зависимости,
строит DAG и запускает независимые задачи параллельно на свободных runner'ах.
После реализации идут тесты и автопроверки, затем независимый агент-ревьюер.
Найденные проблемы возвращают задачу на исправление, после успешного review
изменения мержатся.

Главный принцип: **модель решает задачу, Rivet управляет процессом**.
Переходы между этапами, проверки, повторы, зависимости и блокировки держит
детерминированный код, а не промпт. Все действия пишутся в журнал событий.

## Что в rivet-service

- `cmd/rivetd` — control plane: REST API и SSE для консоли, gRPC для
  runner'ов, встроенная веб-консоль.
- `cmd/rivet-runner` — runner на машине исполнителя: подключается к rivetd,
  забирает стадии задач и ведёт на них агентский цикл Rivet поверх модели
  из каталога подключений. Runner выкатки (`-caps deploy`) работает без
  агента и исполняет только публикации и проверки наблюдения.
- `cmd/rivet` — CLI: миграции, создание базы, просмотр проектов, Epic'ов и
  задач, импорт истории, проверка и отрисовка описания архитектуры проекта
  (`rivet architecture`, формат описан в
  [docs/architecture-format.md](docs/architecture-format.md)).
- `cmd/fake-llm` — детерминированный провайдер моделей для e2e-стенда
  (тестовая инфраструктура, в продукте его нет).
- `internal/` — хранилище (PostgreSQL), оркестратор, планировщик, политики
  (OPA/Rego), SCM-адаптеры GitHub и GitLab, маскировка секретов, протокол
  runner'ов.
- `pkg/protocol` — gRPC-протокол между rivetd и runner'ами.

Состояние хранится в PostgreSQL, транскрипты сессий агентов — в
S3-совместимом хранилище (RustFS в dev).

## Сборка и запуск

Нужны Go 1.26.2 или новее, Docker (для Postgres и S3-хранилища RustFS) и, если пересобирать консоль,
Node.js 24.

Проще всего поднять всё в Docker:

```sh
cd rivet-service
docker compose up -d --build
```

rivetd слушает `127.0.0.1:8080` (API и веб-консоль) и `127.0.0.1:8090`
(gRPC для runner'ов). Первый администратор `admin` / `admin-local`. Эти
значения по умолчанию годятся только для локального стенда, перед
публикацией задайте `RIVET_ADMIN_LOGIN`, `RIVET_ADMIN_PASSWORD` и
`RIVET_SECRET_KEY`.

Установке нужен хостинг кода: задайте `RIVET_SCM=github` и
`RIVET_GITHUB_TOKEN` (в окружении или `.env` рядом с `docker-compose.yml`).
В `docker-compose.yml` без этих переменных стоит `RIVET_SCM=fake`. Это
заглушка хостинга для e2e-стенда: pull request'ы и merge в ней не
настоящие, для работы она не годится.

Локально без контейнера rivetd:

```sh
cd rivet-service
docker compose up -d postgres s3
make build            # go build ./...
RIVET_SCM=github RIVET_GITHUB_TOKEN=ghp_... \
RIVET_ADMIN_LOGIN=admin RIVET_ADMIN_PASSWORD=change-me \
  go run ./cmd/rivetd
```

Миграции базы rivetd применяет сам при старте.

### Подключение моделей

Модели для агентов и декомпозиции Epic берутся из каталога подключений:
«Управление приложением» → «Подключения». Подключение проще всего создать
из пресета провайдера: DeepSeek, OpenAI, Anthropic, OpenRouter, Ollama или
LM Studio. Пресет заполняет тип API и адрес, остаётся вставить ключ
(локальным серверам Ollama и LM Studio ключ не нужен). Список моделей
подключение получает с провайдера кнопкой «Обновить список», а у DeepSeek
модели с окном контекста и пределом ответа есть в самом пресете.

Агент Rivet работает на любой модели включённых подключений. Модель по
умолчанию задаётся на вкладке «Агент Rivet», агенту команды и участнику
процесса модель выбирается парой «подключение / модель». Декомпозицию
можно запустить и без каталога, переменными `ANTHROPIC_API_KEY` или
`DEEPSEEK_API_KEY`.

### Агент Rivet

Агент Rivet ведёт сессию стадии сам: отправляет модели задание и
инструменты (`read_file`, `list_dir`, `search`, `write_file`, `edit_file`,
`run`, `finish`, `ask_human`), исполняет вызовы в рабочей копии и пишет
шаги, транскрипт и расход токенов в сессию. Сторонних программ агента на
runner'е нет.

Лимиты сессии задаются на вкладке «Агент Rivet» (`PUT
/api/v1/system/agents/rivet`, поле `limits`). По умолчанию 80 ходов,
1 000 000 токенов и 30 минут. В лимит токенов идут некешированный вход и
выход: кешированная история, которую цикл повторяет каждый ход, его не
съедает. Длинную историю цикл сжимает сам. Исчерпанный лимит завершает
стадию неуспехом с причиной. Новые лимиты получают следующие сессии,
начатые продолжают со старыми.

Режим доставки ключа на runner задаётся там же. В режиме `secure` (по
умолчанию) ключ подключения уходит в назначение только runner'у,
подключённому по TLS или с loopback, в `always` всегда, в `never` никогда.
Без ключа в назначении runner берёт его из своего окружения:
`RIVET_PROVIDER_KEY_<ID>`, где `<ID>` это идентификатор подключения в
верхнем регистре (`RIVET_PROVIDER_KEY_DEEPSEEK`).

### Runner

Runner подключается с машины, где лежат рабочие копии. Он ведёт агентский
цикл Rivet (`-agent rivet`, значение по умолчанию) и исполняет команды
агента (`run`) и проверки проекта под своим пользователем. Токен
регистрации выпускается в консоли («Управление приложением» →
«Runner'ы»).

Токен привязан к идентификаторам runner'ов (`-id`, по умолчанию имя
хоста; до 128 символов, без пробелов и управляющих символов). При выпуске укажите runner'ы, для которых он предназначен,
например все runner'ы одного хоста. Токен без списка привяжется к первому
runner'у, который с ним зарегистрируется, но не заберёт идентификатор,
привязанный к другому действующему токену. Привязка после выпуска не
меняется: для нового runner'а выпустите новый токен. Runner с чужим
идентификатором получает отказ «токен регистрации не выпущен для
runner'а …» и завершается, а отказ виден на вкладке «Runner'ы» и в
«Аудите» (событие `runner.rejected`). Для ротации выпустите новый токен на
те же runner'ы, перезапустите их с ним и отзовите старый.

**Клиентские сертификаты (mTLS).** Если порт протокола открыт шире
loopback, установка может требовать от runner'ов клиентский сертификат.
rivetd получает корни, которыми подписаны сертификаты runner'ов, в
`RIVET_GRPC_CLIENT_CA` (только вместе с `RIVET_GRPC_TLS_CERT` и
`RIVET_GRPC_TLS_KEY`). Runner без сертификата этих корней, с чужим или
просроченным сертификатом не проходит TLS-рукопожатие, причина пишется в
журнал rivetd. Common Name или DNS-имя из SAN сертификата должно совпадать
с идентификатором runner'а, один сертификат может покрыть несколько
runner'ов хоста через SAN. Токен в этом режиме по-прежнему нужен.

```sh
rivet-runner -plane rivet.example:8090 -id office-1 \
  -tls -tls-ca ca.pem -tls-cert office-1.pem -tls-key office-1-key.pem
```

Ключ сертификата, как и файл токена, принимается только с правами `0600`
и скрыт от команд агента в песочнице. Сертификат перечитывается при
каждом подключении, поэтому для ротации достаточно заменить файлы. Без
`RIVET_GRPC_CLIENT_CA` клиентские сертификаты не проверяются, и если
протокол слушает не только loopback, rivetd предупреждает об этом при
старте.

Runner выкатки запускается с единственной capability `deploy` и без
агента: `rivet-runner -caps deploy`. Он исполняет публикации окружений и
проверки наблюдения, а стадий задач не берёт. Другого агента, кроме
`rivet`, runner объявить не может. Runner старой версии или со сторонним
агентом получает отказ регистрации (событие `runner.rejected` в журнале
установки). Текущая версия runner'а на отказе завершается с причиной, а не
переподключается.

**Где запускать runner для недоверенной модели.** Команда агента `run`
исполняет код, который предложила модель, под пользователем runner'а.
Проверки проекта на шаге test тоже исполняют код модели: тесты и код
задачи в ветке написал агент. На Linux с непривилегированными user
namespaces и команды агента, и проверки идут в песочнице: свои user,
mount, net и pid namespace, доступен только loopback, кеши `GOMODCACHE` и
npm смонтированы только на чтение, а домашний каталог runner'а и файл
токена закрыты в её mount namespace. Это рабочий режим для production.

Требования к хосту для песочницы:

- Linux, непривилегированные user namespaces включены
  (`user.max_user_namespaces` больше нуля, на Ubuntu 24.04 и новее
  `kernel.apparmor_restrict_unprivileged_userns=0` или профиль AppArmor для
  `rivet-runner`);
- в контейнере профиль seccomp должен разрешать user namespaces: профиль
  Docker по умолчанию их запрещает, нужен свой профиль или
  `--security-opt seccomp=unconfined`;
- зависимости проекта скачаны в кеши runner'а до стадии: сети у команд и
  проверок нет, а в кеш они не пишут. Инструменты проверок стоят вне
  `$HOME` runner'а или открыты флагом `-sandbox-ro` (см. «Подготовка кешей
  и флаги runner'а» ниже).

Доступна ли песочница и почему нет, runner пишет в журнал при старте,
вместе с действующими `-unsandboxed`, `-checks-network` и `-sandbox-ro`.

Если песочницы нет (macOS, Linux без user namespaces, Docker с профилем
seccomp по умолчанию), изоляции у команд и проверок **нет**: они идут с
полными правами пользователя runner'а и могут прочитать его файлы, включая
файл токена и ключи подключений, и выполнить произвольный код. Поэтому для
недоверенной модели нужен **Linux с user namespaces, либо отдельная
виртуальная машина или контейнер** на runner. Это требование, а не совет.
Без песочницы runner с агентом Rivet не стартует, а проверки проекта не
запускаются. Чтобы запустить его осознанно (доверенная модель или
локальная отладка), укажите `-unsandboxed` (или
`RIVET_RUNNER_UNSANDBOXED=1`). Тогда runner пишет в журнал предупреждение,
регистрируется без изоляции сети, и консоль помечает его «команды агента с
доступом в сеть».

Запуск под выделенным пользователем на Linux с user namespaces:

```sh
go build -o rivet-runner ./cmd/rivet-runner
sudo useradd -m -r rivet-runner                        # отдельный пользователь без чужих секретов
sudo -u rivet-runner install -m 600 /dev/null /home/rivet-runner/.rivet.token
printf '%s\n' 'rrt_...' | sudo -u rivet-runner tee /home/rivet-runner/.rivet.token >/dev/null
sudo -u rivet-runner env RIVET_RUNNER_TOKEN_FILE=/home/rivet-runner/.rivet.token \
  ./rivet-runner -plane localhost:8090 -agent rivet -caps coding -name "Сервер 1"
```

`-name` (`RIVET_RUNNER_NAME`) задаёт имя runner'а для страницы runner'ов.
Имя, заданное администратором в консоли, важнее.

Защита секретов runner'а ограничена: она закрывает окружение и память
процесса, но **не** файлы на диске, доступные тому же пользователю. Файл
токена и ключи подключений защищает только песочница (скрывает их) или
выделенный пользователь, под которым нет других секретов. На macOS аналога
`PR_SET_DUMPABLE` нет, песочницы нет — режим для отладки, не для
недоверенной модели в production.

Как обрабатываются секреты:

- токен регистрации передавайте файлом с правами `0600` в
  `RIVET_RUNNER_TOKEN_FILE`. Файл с доступом для группы или остальных runner
  не принимает;
- `RIVET_RUNNER_TOKEN`, `RIVET_NATIVE_KEY` и `RIVET_PROVIDER_KEY_<ID>` в
  окружении тоже работают: при старте runner забирает их в память и
  перезапускает себя с очищенным окружением, поэтому в `ps eww` и
  `/proc/<pid>/environ` их нет. Флаг `-token` устарел: значение видно в списке
  процессов до перезапуска;
- если перезапуск с очищенным окружением не удался, runner не стартует:
  секреты остались бы в окружении процесса. Продолжить осознанно можно с
  `RIVET_RUNNER_ALLOW_ENV_SECRETS=1`;
- на Linux процесс runner'а помечен недампируемым (`PR_SET_DUMPABLE=0`): его
  память и окружение не читаются процессами того же пользователя.

Команды агента Rivet (`run`) и проверки проекта получают окружение из
белого списка: `PATH`, `LANG=C.UTF-8`, `TERM=dumb`, `CI=1`, `NO_COLOR=1`,
`GIT_TERMINAL_PROMPT=0`, временные `HOME` и `TMPDIR` с `GOCACHE` в них,
`GOMODCACHE` и `npm_config_cache` на кеши runner'а. Других переменных
окружения runner'а у них нет, поэтому всё, что нужно проверкам, должно
находиться по `PATH` или в кешах. После завершения фоновых процессов не
остаётся. Своего предела времени у проверки нет, её ограничивает время
стадии.

#### Подготовка кешей и флаги runner'а

В песочнице проверка проекта видит рабочую копию, временный `HOME`, кеши
зависимостей только на чтение и системные каталоги. Сети нет: доступен
только свой loopback, поэтому база в Docker на `localhost:5432` хоста тоже
недоступна. Домашний каталог runner'а закрыт пустым каталогом, и
инструменты под ним (`~/.nvm`, `~/go/bin`, `~/.local/bin`, `~/.cargo/bin`)
не находятся, даже если они есть в `PATH`.

Если проверка упала с кодом 127 (команда не найдена) или с типовой сетевой
ошибкой (`network is unreachable`, `could not resolve host`, `ENOTFOUND`,
`EAI_AGAIN`, `dial tcp` и похожие), runner считает это сбоем окружения, а
не красными тестами. Разработчик получает не замечания, а повтор шага без
расхода попытки. Повторный сбой эскалирует человеку с подсказкой «проверке
нужна сеть или инструмент вне рабочей копии».

Как подготовить runner, под его пользователем:

- Go: в клоне проекта выполните `go mod download`, кеш модулей
  (`GOMODCACHE`, по умолчанию `~/go/pkg/mod`) прогреется. Если `go.mod`
  требует другой toolchain, скачайте и его (`go version` в клоне). Проверка
  `go test ./...` берёт модули из кеша, `GOFLAGS=-mod=mod` и
  `-modcacherw` не нужны;
- Node: выполните `npm ci` в клоне проекта, кеш npm (`~/.npm`) прогреется.
  Без сети проверка ставит пакеты только из него (`npm ci --offline &&
  npm test`). Если пакетному менеджеру нужна запись в кеш (pnpm store, yarn
  berry), включите `-checks-network`;
- инструменты ставьте в `/usr/local` или `/opt`. Если они уже лежат под
  `$HOME` (nvm, toolchain Go в `~/sdk`), откройте их каталог флагом
  `-sandbox-ro`;
- проверкам, которым нужны сервисы хоста или скачивание зависимостей,
  включите сеть флагом `-checks-network`.

Флаги runner'а для проверок:

- `-checks-network` (`RIVET_RUNNER_CHECKS_NETWORK=1`): проверки проекта
  идут в песочнице с сетью хоста. `$HOME` runner'а и файл токена
  по-прежнему скрыты, окружение из того же белого списка, а команды агента
  `run` остаются без сети. Это осознанное решение администратора: код из
  ветки задачи получает сеть и может отправить наружу содержимое рабочей
  копии или обратиться к внутренним сервисам;
- `-sandbox-ro <каталог>` (повторяется; `RIVET_RUNNER_SANDBOX_RO`, список
  через `:`): каталог виден в песочнице только на чтение и проверкам, и
  командам агента, например `-sandbox-ro /home/rivet-runner/.nvm
  -sandbox-ro /opt/toolchains`. Флаги в командной строке заменяют список из
  окружения. Runner не стартует, если каталог совпадает с `$HOME` или
  лежит выше него, совпадает с файлом токена или его каталогом, с рабочим
  каталогом runner'а или лежит внутри него. Содержимое каталога читает код модели, секретов там
  быть не должно.

`-unsandboxed` на хосте, где песочница работает, сеть проверкам не
возвращает: изоляция остаётся, а флаг только разрешает работу там, где
песочницы нет.

Кеш сборки Go (`GOCACHE`) у проверок временный: он живёт в `HOME` стадии,
проверки одной стадии его делят, после стадии он удаляется. Каждая стадия
test собирает проект и зависимости заново, на больших проектах это минуты.
Общий кеш на запись не делается: код модели мог бы его отравить для других
проектов. Ускоряют сборку прогретый кеш модулей (не нужно скачивание) и
toolchain, открытый через `-sandbox-ro`, а не скачиваемый заново.

git runner'а не исполняет хуки и `core.fsmonitor` рабочей копии
(`core.hooksPath=/dev/null`, `--no-verify`), игнорирует глобальный и
системный git-конфиг (`GIT_CONFIG_GLOBAL=/dev/null`,
`GIT_CONFIG_SYSTEM=/dev/null`) и объекты-подмены (`GIT_NO_REPLACE_OBJECTS=1`),
а окружение собирает из короткого списка переменных. Служебные файлы `.git`
(config, hooks, commondir, конфигурация подмодулей) и ссылки `refs/replace`
снимаются до сессии агента и до проверок проекта и сверяются после. Если
они изменились, стадия завершается неуспехом с причиной «агент изменил
служебные файлы git», файлы возвращаются к снимку, а если вернуть нельзя,
клон удаляется. Перед каждой стадией рабочая копия приводится к каноничному
состоянию: `refs/replace` чистятся, refspec `origin` возвращается к
стандартному.

### Команда агентов

Работу ведут агенты команды. Каждый агент собран из шаблона роли:
Аналитик, Архитектор, Тимлид, Разработчик, Тестировщик и Ревьюер. Шаблон
задаёт инструкцию, capability и модель по умолчанию. Команда по умолчанию:
Аналитик Вера, Архитектор Ада, Тимлид Тимур, Разработчики Макс и Ева,
Тестировщик Лев и Ревьюер Ирина. Шаблоны и команду настраивают в консоли:
«Управление приложением» → «Шаблоны ролей» и «Команда».

Шаг процесса ссылается на роль, а стадию ведёт свободный агент этой роли на
подходящем runner'е. Агент ведёт одну сессию одновременно, поэтому число
агентов роли задаёт её параллельность. Без агентов роли в команде участник
работает по шаблону на любом runner'е с нужной capability.

На шаге test Тестировщик дописывает тесты по критериям приёмки, затем
проходят проверки проекта. Тестировщик может менять только тестовые файлы
(`test_paths` в политике проекта, по умолчанию `test/**`, `tests/**`,
`**/*_test.*`, `**/*.test.*`, `**/*.spec.*`): остальные его правки runner
откатывает. Выключить тестировщика можно флагом политики `tester_agent: false`.

### Исследование продукта

Владелец проекта загружает интервью пользователей, Аналитик разбирает их в
персоны и потребности с дословными цитатами и предлагает бэклог Epic'ов.
Цитаты, ссылки и зависимости проверяет код. После утверждения бэклога
Epic'и появляются в проекте со ссылками на потребности, Тимлид сразу строит
их планы, а зависимый Epic ждёт завершения тех, от которых зависит. Любой
участник проекта добавляет отзывы пользователей, следующий анализ учитывает
их вместе с интервью. Формат интервью и отзывов, лимиты и разбор
отброшенного описаны в [docs/product-discovery.md](docs/product-discovery.md).

### Цикл разработки

Экран «Цикл разработки» показывает проект как кольцо из восьми фаз:
исследование, архитектура, планирование, разработка, тестирование, ревью,
релиз и сопровождение. Фаза не хранится: её вычисляет `internal/cycle` по
шагу процесса, статусу задачи и состоянию публикаций и инцидентов.
Агрегат отдаёт `GET /api/v1/projects/{id}/cycle?period=today|7d|30d`, а
события задач несут `phase_from` и `phase_to`, когда фаза меняется.

Фаза «Исследование» показывает интервью и отзывы, которых нет в последней готовой
версии исследования, с числом неучтённых отзывов, идущий анализ и бэклог
на утверждении, а в
артефактах интервью и важнейшие потребности. Фаза «Архитектура»
показывает задачи описания архитектуры и Epic'и в исследовании, а в
артефактах снимок архитектуры и последние решения ADR. Пометка «нет
данных» остаётся у проекта без интервью или без описания архитектуры.

Фазы релиза и сопровождения ведут ещё два шаблона: Релиз-инженер Дина
(`devops`) и Инженер сопровождения Глеб (`sre`). Оба работают запросом
control plane к модели агента, без runner'а. Модель берётся у агента
команды, затем у шаблона, затем у планировщика из каталога подключений.
Планировщик из переменных окружения rivetd (`RIVET_LLM_PROVIDER` и ключи)
сюда не входит: Дине и Глебу модель задают в консоли. Без модели или при
ошибке тексты собираются по шаблону. Расход пишется в usage проекта с
ролью шаблона.

**Релизы.** Каждая успешная публикация создаёт релиз. В состав входят
задачи, смерженные после момента версии прошлой успешной публикации
окружения и не позже момента версии этой (создание публикации или
последнее обновление версии, пока она в очереди). Release notes пишет Релиз-инженер, control plane
отбрасывает пункты не из состава и дописывает пропущенные задачи в
«Прочее». Перегенерация доступна владельцу проекта.

**Наблюдение.** В конфигурации окружения задаётся `config.monitor`:
`enabled`, `check_cmd` или `check_url`, `logs_cmd` и `interval_min` (1–1440,
по умолчанию 10). Команду исполняет deploy-runner, объявивший feature
`monitor` (его объявляет runner с capability `deploy`), он же проверяет URL
окружения с собственной доставкой (feature `monitor_url`). Команде проверки
даётся 60 секунд, команде логов 30, общий бюджет передаётся runner'у в
задании. URL окружения с внешней доставкой проверяет control plane и не
ходит на loopback, частные и служебные адреса (см. «Обновление»). Проверка
идёт по интервалу, сразу после успешной публикации и через 2 минуты после
неё, а во время выкатки откладывается. Без подходящего runner'а, при
потере результата или рестарте rivetd во время проверки результат
`unknown`, инцидента нет. Закрытый политикой адрес и недоставленное
runner'у задание повторяются через интервал окружения. История проверок
хранится 7 суток.

**Инциденты.** Провал проверки или публикации открывает инцидент.
Повторы с тем же отпечатком (окружение, источник и нормализованная строка
ошибки) увеличивают счётчик, после трёх провалов подряд серьёзность `high`.
Инженер сопровождения описывает инцидент, затем в Epic «Сопровождение»
появляется задача-баг, которая идёт по обычному процессу и планируется
раньше остальных готовых задач. Релиз с багом смягчает инцидент, три
успешные проверки закрывают его. Провал публикации закрывается релизом
новой версии. Вывод проверок и логи маскируются на runner'е и ещё раз на
control plane.

Лимиты на проект: не больше 3 незавершённых багов из инцидентов и 5 новых
инцидентов за сутки. Сверх лимита инцидент записывается без бага, а в
«needs attention» появляется одна эскалация `OPS_LIMIT`. Баг, отменённый
человеком, сам не пересоздаётся: владелец закрывает инцидент вручную или
командой «создать баг заново» (`POST /api/v1/incidents/{id}/bug`). Той же
командой владелец подтверждает баг по шаблонному описанию (модель была
недоступна): в нём сырые логи, и без человека агенту они не уходят.
Провал публикации из-за потери runner'а или таймаута инцидента не
открывает, остаётся эскалация.

Основные переменные окружения rivetd (полный список — в
`internal/config/config.go`):

| Переменная | Назначение |
|---|---|
| `RIVET_DATABASE_URL` | DSN PostgreSQL |
| `RIVET_HTTP_ADDR`, `RIVET_GRPC_ADDR` | адреса API (`:8080`) и протокола runner'ов (`:8090`) |
| `RIVET_GRPC_TLS_CERT`, `RIVET_GRPC_TLS_KEY` | TLS протокола runner'ов |
| `RIVET_GRPC_CLIENT_CA` | корни клиентских сертификатов runner'ов: включает mTLS |
| `RIVET_S3_ENDPOINT`, `RIVET_S3_ACCESS_KEY`, `RIVET_S3_SECRET_KEY`, `RIVET_S3_BUCKET` | хранилище транскриптов |
| `RIVET_SCM`, `RIVET_GITHUB_TOKEN`, `RIVET_GITHUB_WEBHOOK_SECRET` | хостинг кода и webhook'и |
| `RIVET_SECRET_KEY` | ключ шифрования учётных данных хостингов (32 байта, base64) |
| `RIVET_PUBLIC_URL` | внешний адрес установки для регистрации webhook'ов |
| `RIVET_ADMIN_LOGIN`, `RIVET_ADMIN_PASSWORD` | первый администратор |

### Обновление

**Токены runner'ов привязаны к идентификаторам.** При обновлении каждый
ранее выпущенный токен привязывается к runner'ам, которые уже
регистрировались с ним: по записи runner'а и по журналу регистраций
(`runner.registered`). Эти runner'ы подключаются прежней командой, на
вкладке «Runner'ы» у токена они отмечены «перенесено при обновлении».
Новый runner по старому общему токену больше не регистрируется: выпустите
для него токен с его идентификатором. Токен, по которому никто не
регистрировался, привяжется к первому runner'у. Если такой токен не
нужен, отзовите его: иначе его секрет может занять любой свободный
идентификатор. Идентификатор runner'а теперь проверяется: runner с `-id`
длиннее 128 символов, с пробелами или управляющими символами (например,
`\r` из env-файла) после обновления не регистрируется. Перезапустите его с
допустимым `-id` и выпустите токен на этот идентификатор.

**Переход на агента Rivet (BREAKING).** Сторонние CLI-агенты, их адаптеры
и профили из продукта удалены: агентом может быть только агент Rivet.
Перед обновлением сделайте резервную копию базы, например
`docker compose exec postgres pg_dump -U rivet rivet > rivet-backup.sql`.
Миграция удаляет профили других агентов и переводит агентов команды и
шаблоны ролей на `rivet`, а вернуть прежнюю версию можно только из этой
копии. После обновления:

1. подключите провайдера из пресета («Управление приложением» →
   «Подключения») и выберите модель по умолчанию на вкладке «Агент Rivet»;
2. пересоберите runner'ы и запустите их как `rivet-runner -agent rivet`
   (на машине без песочницы осознанно с `-unsandboxed`), runner выкатки как
   `rivet-runner -caps deploy` без агента;
3. проверьте процессы проектов и переопределения моделей в политиках:
   участник должен ссылаться на агента `rivet` или на модель
   «подключение / модель».

Runner'ы со старым агентом получают отказ регистрации и снимаются с
работы, на странице runner'ов они отмечены «агент не поддерживается».

**Проверки проекта на Linux идут в песочнице (BREAKING).** Раньше проверки
шага test шли на хосте с сетью и полным окружением runner'а. Теперь они
исполняются тем же исполнителем, что и команды агента: без сети, с
закрытым `$HOME` runner'а, окружением из белого списка и кешами
зависимостей только на чтение. Проверка, которой нужно скачать
зависимости, сервис хоста или инструмент из `$HOME` (nvm, `~/go/bin`),
падает сбоем окружения и после повтора эскалирует человеку. Перед
обновлением:

1. прогрейте кеши под пользователем runner'а (`go mod download`, `npm ci`
   в клоне проекта) и перенесите инструменты в `/usr/local` или `/opt`;
2. если инструменты остаются под `$HOME`, запустите runner с
   `-sandbox-ro <каталог>`;
3. если проверкам нужна сеть (сервисы хоста, скачивание при сборке),
   запустите runner с `-checks-network`.

Подробности в разделе «Подготовка кешей и флаги runner'а».

С циклом разработки control plane проверяет URL (Verify внешней доставки,
синхронизация GitOps, наблюдение окружений с внешней доставкой) только на
публичных адресах: loopback, частные сети, link-local (метаданные облака),
CGNAT, служебные диапазоны и IPv4 внутри NAT64 и 6to4 закрыты. Прокси из
окружения при этом не используется, потому что обошёл бы фильтр.

Перед обновлением проверьте окружения с внешней доставкой и GitOps:

- `verify_url` смотрит во внутреннюю сеть (`10.x`, `172.16–31.x`,
  `192.168.x`, `*.internal`, staging за VPN) — задайте
  `RIVET_ALLOW_PRIVATE_URLS` списком нужных диапазонов, например
  `10.0.0.0/8,192.168.0.0/16`, или `true`;
- установка выходит наружу только через прокси (`HTTPS_PROXY`) — нужен
  `RIVET_ALLOW_PRIVATE_URLS=true`: с ним фильтр снят и прокси работает.

Без этого публикация на закрытый адрес проваливается без отката и
инцидента, а в «needs attention» появляется эскалация с причиной «адрес во
внутренней сети запрещён политикой установки, задайте
RIVET_ALLOW_PRIVATE_URLS». Наблюдение такого окружения показывает `unknown`
с той же причиной. Окружения с собственной доставкой (ssh, Kubernetes) это
не касается: их Verify и проверки идут из сети deploy-runner'а.

Runner'ы стоит пересобрать: проверки наблюдения получают только runner'ы с
feature `monitor`, URL-проверки — с `monitor_url`.

### Тесты

```sh
cd rivet-service
go test ./...                       # без базы тесты хранилища пропускаются
docker compose up -d postgres
RIVET_DATABASE_URL='postgres://rivet:rivet@localhost:5432/rivet?sslmode=disable' go test ./...
make fuzz                           # короткий фаззинг по всем таргетам
make lint                           # golangci-lint
```

Сквозные тесты живут в [rivet-e2e](https://github.com/PavluninVladimir/rivet-e2e):
стенд поднимает `rivet-service/scripts/e2e-stand.sh`. Это тестовая
инфраструктура: модель там `cmd/fake-llm`, хостинг `RIVET_SCM=fake`, а
runner'ы стартуют с `RIVET_RUNNER_UNSANDBOXED=1`.
