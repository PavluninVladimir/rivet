# Нагрузочное тестирование локального релиза

После первого рабочего релиза local_docker Rivet сохраняет один вопрос на окружение: какую нагрузку должно выдерживать приложение. После обновления существующие здоровые публикации получают тот же вопрос без повторной выкатки. «Позже» сохраняет отсрочку. Сам вопрос, переподключение runner и очередная проверка здоровья не создают нагрузку.

Владелец проекта явно задаёт конечный профиль и запускает попытку: VUs с think time не меньше секунды либо RPS, target, предел поиска, длительность target, p95 и допустимую долю ошибок. Можно указать 1–5 относительных GET-путей с весами, ожидаемым 2xx и Content-Type. RPS — HTTP-запросы в секунду, один GET на итерацию. Сценарий описывает выбранную смесь чтения. Он не измеряет универсальную мощность приложения и не выполняет произвольные JS, shell или операции изменения данных.

Сначала выполняется target, затем не более трёх возрастающих ступеней по 20 секунд до явного предела. Следующая ступень получает отдельное разрешение после сохранения предыдущих измерений и проверки активного назначения. При нарушении SLO повышение прекращается. В отчёте отдельно указаны результат target и capacity: достигнутый предел, граница SLO либо недостаточно данных. Пропущенные итерации, недостигнутый RPS и неполное покрытие смеси не считаются доказанной мощностью системы. Нулевая доля ошибок проходит при фактическом нуле; p95 допускает 1–5000 мс.

## Выделенный runner

Установите проверенный native k6 2.4.x на том же хосте, где работает Docker-runner публикации. Стабильные k6 2.3.x также поддерживаются; другие семейства и предварительные версии отклоняются при запуске runner и перед исполнением задания. Имена host у этих двух runner должны совпадать. Образ Docker для k6 не нужен. Отдельному runner выдаётся отдельный scoped токен обычным процессом регистрации Rivet.

```sh
rivet-runner -id rivet-local-k6 -name 'Нагрузочное тестирование k6' \
  -caps load -k6-bin /opt/homebrew/bin/k6 \
  -plane localhost:8090 -tls -tls-ca /path/to/server.crt \
  -workdir /path/to/private/k6-runner
```

Токен задаётся через RIVET_RUNNER_TOKEN_FILE; не включайте его в команду. Вместо `-k6-bin` можно использовать RIVET_K6_BIN. Для долгоживущего runner указывайте путь к проверенной установке (например, `/opt/homebrew/Cellar/k6/2.4.0/bin/k6`), чтобы обновление общей ссылки Homebrew не меняло версию автоматически. Единственная capability — load; агент и модели не задаются. Этот процесс не выполняет кодирование, review, выкатки, проверки наблюдения и задания хостов. Протокол существующих runner не повышает минимальную версию: load использует аддитивную feature k6_load_v1.

Авторизация теста только явно выбранным существующим секретом окружения: Authorization или Cookie, значение секрета — полное значение заголовка. Передача требует защищённого канала. Секрет находится в закрытом временном файле, удаляемом перед финальным результатом. Он не передаётся в аргументах или окружении k6, не попадает в отчёт, outbox или события. Native k6 получает очищенные env/config без пользовательских экспортов, proxy и cloud. Docker inspect читает только identity/labels/port, без Config.Env приложения.

## Конечные лимиты установки

| Переменная control plane | По умолчанию |
| --- | ---: |
| RIVET_LOAD_MAX_VUS | 100 |
| RIVET_LOAD_MAX_RPS | 500 |
| RIVET_LOAD_MAX_TARGET_DURATION_S | 120 |
| RIVET_LOAD_MAX_RUN_DURATION_S | 300 |

Все лимиты — положительные конечные числа; target duration не меньше 10 секунд. Пределы доступны форме через API. Их можно осознанно повысить. Попытка хранит снимок лимитов; перед выдачей runner применяется более строгий из снимка и текущих настроек. Бюджет включает preflight, все ступени, grace и cleanup. Общий дедлайн неизменяем, фиксированный скрипт также прекращает запросы по абсолютному времени.

Попытка привязана к конкретным release/publication/version/generation/container и loopback-порту. Stop/restart/remove, новая публикация и удаление окружения атомарно прерывают её. Повтор и изменение публикации ждут подтверждения остановки процесса или конечного дедлайна. Пока идёт тест, технический reconcile Docker-публикации откладывается: он сам может перезапускать контейнер, что исказило бы измерения. Потерянные или неоднозначно доставленные попытки автоматически не повторяются; требуется новый явный запуск. Заведомо не поставленное в канал задание может остаться в очереди.

Генератор делит хост с приложением. Жёсткая изоляция CPU/памяти средствами ОС не заявляется; при нехватке генератора результат — inconclusive. В CI используется официальный k6 2.4.0 с закреплённым SHA-256; fixtures создают собственные HTTP-серверы и временные БД, рабочие приложения не нагружаются.
