# Описание архитектуры проекта

Rivet читает описание архитектуры из репозитория проекта, из каталога `docs/architecture/`. Описание необязательно: если каталога нет, Rivet считает, что у проекта нет описания, и это не ошибка.

Описание пишут агенты и люди. Rivet проверяет его детерминированным кодом, без модели, и рисует диаграммы Mermaid, которые GitHub показывает прямо в PR. Модель повторяет слои TOGAF (бизнес, приложения, данные, технологии) на подмножестве ArchiMate 3.2, бизнес-процессы хранятся в BPMN 2.0.

Полный пример лежит в [`rivet-service/internal/architecture/testdata/shop`](../rivet-service/internal/architecture/testdata/shop): небольшой интернет-магазин с четырьмя слоями, двумя процессами, собственным viewpoint'ом и изменением «Возвраты заказов».

## Быстрый старт

```sh
rivet architecture init -system "Интернет-магазин"   # пустое описание в docs/architecture
rivet architecture validate                          # проверить описание и все изменения
rivet architecture views                             # перерисовать views/
```

Все команды работают с локальным каталогом и не обращаются к control plane. Флаг `-dir` задаёт другой каталог описания.

## Раскладка

```
docs/architecture/
  architecture.yaml          манифест
  model/
    business.yaml            бизнес-слой
    application.yaml         слой приложений
    data.yaml                слой данных
    technology.yaml          слой технологий
    <viewpoint>.yaml         документ собственного viewpoint'а
  processes/<id>.bpmn        процессы, имя файла совпадает с id элемента process
  scenarios/<id>.yaml        сценарии взаимодействия из индекса манифеста
  adr/NNNN-<slug>.md         архитектурные решения из индекса манифеста
  viewpoints/<id>.yaml       определения собственных viewpoint'ов
  views/                     сгенерированные представления, руками не править
    hld.md                   обзорный документ
    c4/                      схемы C4 и экспорт Structurizr DSL
  changes/<id>/              изменения, которые ещё не применены
  changes/archive/<дата>-<id>/
```

Пути выводятся из манифеста и модели, поэтому описание читается без обхода каталога. Отсутствующий файл слоя равен пустому слою. Симлинк, который ведёт за пределы каталога описания, не читается и не перезаписывается: команда завершается ошибкой. О лишних файлах в `model/`, `processes/` и `viewpoints/` проверка предупреждает: чаще всего это опечатка в имени. О файлах в `scenarios/` и `adr/`, которых нет в индексе манифеста, проверка тоже предупреждает: снимок архитектуры в консоли их не прочитает.

## Манифест

```yaml
format: rivet.architecture/v1
system: Интернет-магазин
description: Продаёт товары покупателям и ведёт заказы до доставки
principles:
  - id: p.single-order-source
    title: У заказа один источник истины
    rationale: Состояние заказа меняет только сервис заказов
viewpoints: [security]
scenarios: [sc.checkout, sc.refund]
decisions: [0001-postgres, 0002-event-bus]
```

`format` проверяется первым. Если версия неизвестна, проверка останавливается с ошибкой `format.unsupported` и остальные файлы не разбирает. `system` называет описываемую систему, необязательное `description` в одном-двух предложениях говорит, зачем она нужна: это назначение системы в HLD и на схеме контекста C4. Принципы архитектуры задают правила проекта, которые видят агенты и ревьюер, идентификаторы принципов не должны повторяться. `viewpoints` перечисляет собственные viewpoint'ы проекта. `scenarios` и `decisions` задают индекс сценариев и архитектурных решений: читаются только перечисленные файлы.

## Модель

Файл слоя содержит массив `elements`:

```yaml
elements:
  - id: app.orders
    type: component
    name: Сервис заказов
    description: Хранит заказы и меняет их статус
    props: {language: go, replicas: 3}
    relations:
      - {type: realization, to: app.order-api}
      - {type: access, to: data.order, mode: write}
```

`id`, `type` и `name` обязательны. Идентификатор подходит под шаблон `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)+$` и уникален во всём описании. Префикс слоя (`biz.`, `app.`, `data.`, `tech.`) не обязателен, но помогает читать связи. В `props` лежат строки, числа и логические значения. Неизвестные поля дают ошибку: опечатка в имени поля не должна молча пропадать.

YAML разбирается строго: один документ в файле, без якорей, ссылок `*name`, ключей слияния `<<` и нестандартных тегов.

### Типы элементов

| Слой | Файл | Типы |
|---|---|---|
| Бизнес | `model/business.yaml` | `actor`, `role`, `business-service`, `process`, `business-object` |
| Приложения | `model/application.yaml` | `component`, `interface`, `application-service` |
| Данные | `model/data.yaml` | `data-object` |
| Технологии | `model/technology.yaml` | `node`, `system-software` |

Элемент лежит в файле своего слоя.

### Связи

Связь хранится у источника и указывает на цель полем `to`. Допустимые пары:

| Связь | Источник → цель |
|---|---|
| `composition` | элементы одного слоя |
| `association` | любые элементы |
| `assignment` | actor → role · actor, role → process · node → system-software |
| `realization` | process → business-service · component → application-service · data-object → business-object · component, application-service → process |
| `serving` | business-service → actor, role, process · application-service, interface, component → component, process, role, actor · node, system-software → component, node, system-software |
| `access` | process, component, application-service → business-object, data-object · system-software → data-object |
| `flow`, `triggering` | process → process · component → component |

У `access` есть необязательный `mode`: `read`, `write` или `readwrite`. У других связей `mode` не задаётся.

## Нотация C4

Отдельной модели C4 нет: людей, системы, контейнеры и компоненты Rivet выводит из той же модели слоёв. Описываемая система берётся из `system` манифеста, её назначение из `description`.

| Элемент модели | Вид C4 по умолчанию |
|---|---|
| `actor`, `role` | человек, при `external: true` внешний |
| `component` без родителя | контейнер описываемой системы, при `c4: system` программная система, при `external: true` внешняя система |
| `component` в `composition` контейнера | компонент этого контейнера, более глубокие потомки относятся к ближайшему контейнеру |
| `system-software` с `access` к `data-object` | база данных описываемой системы |
| `system-software` с `c4: queue` | очередь описываемой системы |
| `interface`, `application-service` | не рисуются, их связи переходят к владельцу (`composition`) или реализующему (`realization`) |
| остальное | не рисуется |

Вывод уточняют три зарезервированных ключа `props`:

- `c4` задаёт вид явно: `person`, `system`, `container`, `database`, `queue`, `component` или `none` (не рисовать). Допустимые значения зависят от типа: `actor` и `role` бывают `person`, `component` любым видом, кроме `person`, `system-software` контейнером, базой или очередью.
- `technology` — строка с технологией, она подписывается на схемах.
- `external: true` помечает внешнего человека или внешнюю систему. Ключ задаётся только у элемента без родителя.

```yaml
elements:
  - id: app.payments
    type: component
    name: Платёжный шлюз
    props: {c4: system, external: true}
  - id: tech.queue
    type: system-software
    name: Очередь событий
    props: {c4: queue, technology: RabbitMQ}
```

Компонент верхнего уровня с `c4: system` становится программной системой, а его дети по `composition` её контейнерами. Так описывается ландшафт из нескольких систем. Без явного вида такие компоненты остаются контейнерами описываемой системы.

Связи C4 выводятся из связей модели. `serving` A → B рисуется как B → A «использует», `flow` как «передаёт», `triggering` как «вызывает». `access` компонента к объекту данных, который хранит база, превращается в связь компонента с базой «читает X», «пишет X» или «читает и пишет X» по `mode`. На схеме уровнем выше концы связи поднимаются к видимому предку: компонент к контейнеру, контейнер к системе. Петли отбрасываются, одинаковые связи склеиваются, подписи сортируются и объединяются через запятую.

Схема развёртывания строится, если в модели есть хотя бы один `node`. Узлы и системное ПО вне C4 становятся узлами развёртывания, вложенность задают `composition` и `assignment` между ними. Контейнер попадает на узел, который его обслуживает связью `serving`. Тип узла берётся из `technology`.

Ошибки правил `c4.*` бывают только при явно заданных свойствах, поэтому описание без них всегда корректно с точки зрения C4:

| Код | Что не так |
|---|---|
| `c4.kind-unknown` | неизвестное значение `c4` |
| `c4.kind-type` | вид недопустим для типа элемента |
| `c4.prop-type` | `c4` или `technology` не строка, `external` не логическое значение |
| `c4.external-nested` | `external` у элемента, который входит в `composition` |
| `c4.container-parent` | контейнер входит не ровно в одну программную систему |
| `c4.component-parent` | компонент входит не ровно в один контейнер |
| `c4.ambiguous-parent` | предупреждение: элемент входит в несколько возможных родителей, выбран родитель с меньшим идентификатором |

## Бизнес-процессы

Процесс описывается элементом типа `process` в бизнес-слое и файлом `processes/<id>.bpmn` в формате BPMN 2.0 XML. Файл можно рисовать в Camunda Modeler или bpmn.io, координаты диаграммы (BPMN DI) необязательны.

Ссылки на модель задаёт атрибут `rivet:ref` в пространстве имён `urn:rivet:architecture:1`:

```xml
<bpmn:definitions xmlns:bpmn="http://www.omg.org/spec/BPMN/20100524/MODEL"
                  xmlns:rivet="urn:rivet:architecture:1">
  <bpmn:process id="checkout">
    <bpmn:laneSet id="lanes">
      <bpmn:lane id="lane-buyer" name="Покупатель" rivet:ref="biz.buyer">
        <bpmn:flowNodeRef>start</bpmn:flowNodeRef>
      </bpmn:lane>
    </bpmn:laneSet>
    <bpmn:serviceTask id="create-order" name="Создать заказ" rivet:ref="app.order-api"/>
    ...
```

Дорожка ссылается на `role` или `actor`, сервисная задача на `component` или `application-service`. Редакторы на bpmn-js сохраняют атрибут при правке, но в интерфейсе его не показывают, поэтому добавлять его проще в XML.

Поддерживается подмножество: процесс, дорожки, события `startEvent`, `intermediateCatchEvent`, `intermediateThrowEvent`, `endEvent`, задачи `task`, `userTask`, `serviceTask`, `manualTask`, шлюзы `exclusiveGateway`, `parallelGateway`, потоки `sequenceFlow`. Остальные элементы (подпроцессы, граничные события, другие шлюзы и задачи) дают предупреждение `bpmn.unsupported`. Через них всё равно проходит обход графа, поэтому ложных тупиков нет. Если в файле несколько пулов, проверяется первый.

Структура проверяется так:

- Есть хотя бы одно начальное и одно конечное событие.
- Каждый узел достижим из начального события.
- Из каждого узла достижимо конечное событие.
- Источник и цель каждого потока существуют.
- У ветвящего шлюза не меньше двух исходящих потоков.

## Собственные viewpoint'ы

Viewpoint определяет часть архитектуры: какой документ её описывает, как его проверять, какое задание получает агент и как её рисовать. Четыре встроенных viewpoint'а совпадают со слоями. Свой viewpoint проект объявляет в манифесте и описывает файлом `viewpoints/<id>.yaml`:

```yaml
id: security
title: Угрозы и меры защиты
prompt: |
  Опиши угрозы для компонентов и интерфейсов и меры против них.
items: /threats              # JSON Pointer на массив записей с полем id
schema:                      # JSON Schema документа model/security.yaml
  type: object
  required: [threats]
  properties:
    threats:
      type: array
      items:
        type: object
        required: [id, title, targets]
        properties:
          id: {type: string}
          title: {type: string}
          targets: {type: array, items: {type: string, x-rivet-ref: true}}
render:
  kind: graph                # graph или table
  label: title
  edges: [targets]
```

- `prompt` получает агент, когда описывает этот viewpoint.
- `items` указывает на массив записей. Записи адресуются по `id`, по нему же их меняет дельта. Идентификаторы записей подчиняются тому же шаблону, что элементы модели, и не должны совпадать с ними.
- `schema` задаёт JSON Schema документа (draft 2020-12). Внешние `$ref` (файлы и URL) не загружаются.
- `x-rivet-ref: true` помечает строку как ссылку на элемент основной модели. Такие ссылки проверяются так же, как связи. Пометка учитывается в `properties`, `items`, `prefixItems`, `patternProperties`, `additionalProperties`, `allOf` и локальных `$ref` вида `#/$defs/x` или `#якорь` (`$anchor`). Другие `$ref` и `$dynamicRef` в схеме собственного viewpoint'а запрещены. В условных ветках (`if`/`then`/`else`, `anyOf`, `oneOf`, `not`, `contains`, `dependentSchemas`) она запрещена: применимость ветки зависит от значения, и проверка не может однозначно сказать, ссылка это или текст.
- `render.kind: graph` рисует записи узлами и проводит рёбра по полям из `edges`. Поля в `edges` должны быть помечены `x-rivet-ref`. `render.kind: table` рисует таблицу, колонки задаёт `columns` или берутся все поля записей.

Идентификатор собственного viewpoint'а не может совпадать со встроенным. Имена `readme`, `hld` и `adr` тоже заняты: под ними генерируются `views/README.md`, `views/hld.md` и `views/adr.md`.

## Данные (ERD)

У объекта данных `data-object` можно описать атрибуты, а у связи `association` между объектами данных кардинальность и подпись:

```yaml
elements:
  - id: data.contact
    type: data-object
    name: Контакт
    attributes:
      - {name: id, type: uuid, pk: true}
      - {name: company_id, type: uuid, fk: {to: data.company, attribute: id}, nullable: true}
      - {name: email, type: string, unique: true}
    relations:
      - {type: association, to: data.deal, cardinality: one-to-many, label: участвует}
```

- Атрибут: `name`, `type` (свободная строка: `uuid`, `varchar(64)`, `timestamptz`), `pk`, `fk`, `nullable`, `unique`, `description`.
- Кардинальность: `one-to-one`, `one-to-many`, `many-to-one`, `many-to-many`.
- У объекта с атрибутами должен быть первичный ключ, а `pk` не бывает `nullable`. Внешний ключ ссылается на существующий объект данных и его атрибут.
- Внешний ключ без явной связи даёт связь «многие к одному» от ссылающегося объекта. Если для пары объектов есть и явная связь с кардинальностью, рисуется она.
- Хранилищем считается `system-software`, которое C4 считает базой данных, и объекты данных, к которым у него есть `access`. Для каждого хранилища строится своя ERD.
- На схеме атрибуты идут в стабильном порядке: первичные ключи, затем остальные по имени. Перестановка в файле схему не меняет.
- Имена и типы атрибутов на схеме сводятся к латинице, цифрам и подчёркиванию. К словам `pk`, `fk` и `uk` в любом регистре добавляется подчёркивание, исходное имя и тип уходят в комментарий атрибута. В подписях `%` и обратная косая черта заменяются на `％` и `∖`, чтобы Mermaid не принял их за комментарий или escape. Объект без имени подписывается идентификатором.

## Сценарии

Ключевые потоки вызовов описываются в `scenarios/<id>.yaml` и перечисляются в `scenarios` манифеста:

```yaml
id: sc.contact-create
title: Создание контакта
process: biz.lead-intake           # необязательно, элемент типа process
participants: [biz.manager, app.web, app.api, tech.db]
steps:
  - {from: biz.manager, to: app.web, message: заполняет форму, kind: sync}
  - {from: app.web, to: app.api, message: POST /api/contacts, kind: sync}
  - alt:
      - when: email уже есть
        steps:
          - {from: app.api, to: app.web, message: 409 возможный дубль, kind: return}
      - when: иначе
        steps:
          - {from: app.api, to: tech.db, message: запись, kind: sync}
  - loop:
      when: для каждого вложения
      steps:
        - {from: app.api, to: app.api, message: проверяет файл, kind: self}
```

- Участники: элементы `actor`, `role`, `component`, `system-software`, `node` и описываемая система `system`. Порядок участников задаёт `participants`, иначе порядок первого появления.
- Вид шага: `sync`, `async`, `return`, `self` (от участника к нему же).
- Блоки: `alt` (список веток `{when, steps}`), `opt` и `loop` (`{when, steps}`), вложенность до 4 уровней.
- Шаг между участниками, у которых в модели нет связи ни в одну сторону, даёт предупреждение `scenario.no-relation`. Связь ищется и по иерархии C4: компонент поднимается к контейнеру, и связь контейнера, прямая или на схеме C4, покрывает шаг компонента.
- Псевдонимы участников на схеме совпадают с псевдонимами C4. Участник вне C4 получает свободный псевдоним, который не совпадает ни с элементами C4, ни с другими участниками.

## Архитектурные решения (ADR)

Решения лежат в `adr/NNNN-<slug>.md`, нумерация подряд с `0001`, имена перечисляются в `decisions` манифеста. Структурные поля в YAML front matter, тело в формате MADR:

```markdown
---
number: 3
title: Хранилище в JSON-файле
status: accepted          # proposed, accepted, superseded, deprecated, rejected
date: 2026-11-04
elements: [tech.json-file, app.api]
supersedes: []
superseded_by: null
---

## Контекст
## Решение
## Последствия
## Рассмотренные варианты
```

- Разделы «Контекст», «Решение», «Последствия» обязательны, английские `Context`, `Decision`, `Consequences` тоже принимаются.
- Удалять решения нельзя, поэтому дыр в нумерации не бывает: вместо удаления статус `deprecated` или `rejected`.
- Замена взаимна: если решение 4 заменяет 1 (`supersedes: [1]`), у решения 1 статус `superseded` и `superseded_by: 4`.
- Заменять можно только решения с меньшим номером, а `superseded_by` указывает на больший номер. Поэтому циклов замены не бывает.
- Элемент из `elements`, которого нет в модели, у решений `proposed` и `accepted` даёт ошибку `adr.element`. У `superseded`, `deprecated` и `rejected` это предупреждение: решение остаётся в журнале историей и не мешает удалить элемент.
- Тело решения хранится как есть, с исходными переводами строк. При правке front matter перевод строки файла сохраняется.

## Изменение архитектуры

Изменение описывает переход от текущего состояния к целевому и лежит в `changes/<id>/`:

```
changes/refunds/
  change.yaml              id, title, необязательная ссылка на Epic (epic)
  vision.md                видение: цель, рамки, заинтересованные лица
  delta/<viewpoint>.yaml   дельта по viewpoint'у
  processes/<id>.bpmn      целевые процессы
  scenarios/<sid>.yaml     целевые сценарии, перечислены в поле scenarios файла change.yaml
  adr/NNNN-<slug>.md       новые решения, перечислены в поле decisions файла change.yaml
  gap.yaml                 разрывы
```

Дельта состоит из трёх разделов:

```yaml
added:                     # новые элементы целиком
  - {id: app.refunds, type: component, name: Сервис возвратов}
modified:                  # изменённые элементы целиком, вместе со всеми связями
  - {id: app.storefront, type: component, name: Витрина, relations: [...]}
removed:                   # удаляемые элементы с причиной
  - {id: app.mail-refunds, reason: Возвраты переезжают в сервис возвратов}
```

Целевой процесс с id существующего процесса заменяет его, с новым id добавляет новый. Новому элементу `process` нужен целевой процесс.

Разрыв связывает изменение с причиной:

```yaml
gaps:
  - id: gap.refund-service
    title: Нет сервиса возвратов
    kind: add                # add, change или remove
    description: Витрине нужна форма возврата, а заказам сервис, который меняет их статус
    elements: [app.refunds, app.storefront]
    processes: [biz.refund]
    scenarios: [sc.refund]   # целевые сценарии изменения
```

Проверка изменения требует:

- Добавляемых id нет в текущей модели, изменяемые и удаляемые есть в файле своего слоя.
- Каждая запись дельты, каждый целевой процесс и каждый целевой сценарий покрыты хотя бы одним разрывом.
- Новые решения нумеруются продолжением журнала текущего описания. Решение с `supersedes` в целевом описании переводит заменяемое в `superseded`.
- Разрыв ссылается только на записи дельты и целевые процессы этого изменения.
- Целевая модель, то есть текущая с применённой дельтой, проходит все проверки модели и процессов.
- На удаляемый элемент в целевой модели не осталось ссылок.

Ошибки целевой модели указывают на файл, откуда пришла запись: на дельту для новых и изменённых записей и на файл модели для остальных. Если изменение исправляет ошибку текущей модели, проверка изменения её уже не показывает.

## Дефекты

Проверка находит все дефекты за один проход. Каждый дефект содержит важность (`error` или `warning`), код правила, файл, место (id записи или JSON Pointer) и сообщение. Описание корректно, если в нём нет ошибок.

```
error model/application.yaml app.a [ref.unresolved] связь flow ссылается на несуществующий элемент app.b
```

`rivet architecture validate -json` выводит дефекты массивом JSON с полями `severity`, `rule`, `file`, `location`, `message`. Коды правил стабильны: по ним агенты и тесты понимают, что исправлять. Основные коды:

| Код | Что значит |
|---|---|
| `format.unsupported` | неизвестная версия формата |
| `yaml.parse`, `schema.violation` | файл не разбирается или нарушает схему |
| `id.pattern`, `id.duplicate` | идентификатор не подходит под шаблон или занят |
| `element.type-unknown`, `element.layer` | неизвестный тип или элемент не в своём слое |
| `ref.unresolved` | ссылка на несуществующий элемент |
| `relation.not-allowed`, `relation.mode` | недопустимая связь или режим доступа не у `access` |
| `process.file-missing` | у элемента `process` нет файла BPMN |
| `bpmn.*` | разбор и структура процесса, ссылки `rivet:ref` |
| `viewpoint.*` | определение собственного viewpoint'а |
| `delta.added-exists`, `delta.target-missing` | дельта не применима к текущей модели |
| `delta.uncovered`, `process.uncovered`, `gap.ref-outside` | дельта и разрывы не сходятся |
| `delta.removed-in-use` | удаляемый элемент ещё используется |
| `erd.*` | атрибуты, ключи и кардинальность объектов данных |
| `scenario.*` | сценарии: участники, процесс, пустые блоки, глубина, `scenario.no-relation` (предупреждение) |
| `adr.*` | решения: имя, front matter, нумерация, статус, дата, разделы, замена и её порядок (`adr.supersede-target`), элементы (`adr.element`, у неактивных решений предупреждение) |
| `change.scenario-uncovered`, `change.adr-numbering` | целевой сценарий без разрыва, номер нового решения не продолжает журнал |
| `apply.scenario-exists`, `apply.adr-exists` | при применении файл сценария или решения уже лежит в описании вне индекса |
| `views.stale` | представления не соответствуют описанию |

## Представления

`rivet architecture views` пишет в `views/` Markdown с диаграммами Mermaid:

- `README.md` с принципами и ссылками на остальные представления.
- По файлу на каждый слой и собственный viewpoint.
- `processes/<id>.md` с блок-схемой каждого процесса.
- `erd/all.md` с общей ERD и `erd/<store-id>.md` с ERD каждого хранилища.
- `scenarios/<id>.md` с sequence-схемой каждого сценария.
- `adr.md` с реестром решений.
- `c4/context.md` со схемой контекста (L1), `c4/container/<system>.md` со схемой контейнеров каждой системы (L2), `c4/component/<container-id>.md` со схемой компонентов контейнера (L3) и `c4/deployment.md` со схемой развёртывания, если в модели есть узлы. Для описываемой системы `<system>` равен `system`. Схемы в нотации Mermaid C4, GitHub рисует их в PR.
- `c4/workspace.dsl` с полной моделью в Structurizr DSL: модель, окружение развёртывания и виды. Идентификаторы DSL выводятся из идентификаторов элементов, всё, кроме строчных букв и цифр, заменяется на `_`, редкие совпадения разводятся суффиксом `_2`. Файл открывается в Structurizr и других инструментах C4.
- `hld.md` с обзором по разделам: назначение и принципы, контекст (L1), контейнеры (L2), ключевые бизнес-процессы, данные, развёртывание, внешние интеграции, ключевые сценарии, архитектурные решения (только принятые) и изменения архитектуры в работе. Пустой раздел прямо говорит, чего в описании нет. «Данные» ссылается на ERD.
- `changes/<id>-c4.md` с целевыми схемами контекста, контейнеров и затронутых компонентов изменения: добавленное, изменённое и удалённое подсвечено, под схемами легенда.
- `changes/<id>.md` для каждого корректного изменения: видение, целевая модель с подсветкой добавленного, изменённого и удалённого, таблица разрывов, целевые процессы, целевые сценарии и новые решения. Целевые сценарии рисуются в `changes/<id>-scenarios.md`, поэтому id изменения не может оканчиваться на `-c4` и `-scenarios`.

Генерация детерминирована: одно и то же описание даёт побайтно одинаковые файлы. Каталог `views/` целиком создаётся генератором, ручные правки в нём перезаписываются. Слой, в котором больше 60 элементов, рисуется отдельной диаграммой на каждый тип.

## Применение изменения

```sh
rivet architecture apply -change refunds
```

Команда заново проверяет изменение, добавляет, заменяет и удаляет записи в файлах модели, кладёт целевые процессы в `processes/`, удаляет BPMN удалённых процессов, переносит папку изменения в `changes/archive/<дата>-<id>/` и перерисовывает `views/`. Сценарии изменения заменяют или дополняют текущие, новые решения переносятся в `adr/`, у заменённых решений в front matter меняются `status` и `superseded_by` (тело не трогается), индекс манифеста дополняется. Файлы правятся на уровне узлов YAML: комментарии и порядок нетронутых записей сохраняются, дифф в PR остаётся минимальным.

Если текущая модель ушла вперёд, например кто-то уже добавил элемент с тем же id или решение с тем же номером, команда перечисляет все конфликты и не меняет ни одного файла. Файл сценария или решения, который лежит в описании, но не перечислен в индексе манифеста, тоже конфликт (`apply.scenario-exists`, `apply.adr-exists`): команда его не перезаписывает.

## Проверка в CI проекта

Команды завершаются с кодом 0, если ошибок нет, 1 при ошибках, конфликтах и устаревших представлениях и 2 при неверных аргументах. Рецепт для GitHub Actions:

```yaml
name: architecture
on:
  pull_request:
    paths: ['docs/architecture/**']
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/checkout@v4
        with:
          repository: PavluninVladimir/rivet
          path: .rivet
      - uses: actions/setup-go@v5
        with:
          go-version-file: .rivet/rivet-service/go.mod
      - run: cd .rivet/rivet-service && go build -o "$RUNNER_TEMP/rivet" ./cmd/rivet
      - run: $RUNNER_TEMP/rivet architecture validate
      - run: $RUNNER_TEMP/rivet architecture views --check
```

Рецепт собирает CLI той же версии, что Rivet. Старая версия CLI отклонит манифест с полями, которых она не знает, например `description`.

Новая версия Rivet может добавить представления (так появились `views/c4/` и `views/hld.md`). Тогда `views --check` в CI проекта падает с `views.stale`, хотя описание не менялось. Лечится перегенерацией одним коммитом:

```sh
rivet architecture views
git add docs/architecture/views && git commit -m "Перегенерировать представления архитектуры"
```

Снимок архитектуры в консоли Rivet от `views/` в репозитории не зависит: схемы и HLD он строит сам из модели.

## Проверка на шаге test

Задачи Rivet проверяют описание сами, отдельный CI для этого не нужен. В проекте, где у снимка есть описание, к проверкам шага test добавляется проверка «Архитектура». Она зовёт подкоманду runner'а:

```sh
"$RIVET_RUNNER_BIN" architecture gate -base origin/main
```

Если ветка задачи не меняет `docs/architecture/`, проверка сразу проходит. Иначе она гоняет `validate` и `views --check` и печатает дефекты, они попадают в замечания для исправления. У задачи описания архитектуры проверка обязательна (`-force`), а файлы вне `docs/architecture/` её проваливают (`-only-docs`). Ту же границу control plane перед merge сверяет по списку файлов PR на хостинге: проверке в рабочей копии он не доверяет, потому что состояние `.git` агент может подменить. Runner без подкоманды `architecture` пропускает ветку без изменений описания, а ветку с изменениями проваливает с просьбой обновить rivet-runner.

У runner'а те же команды, что у CLI `rivet`: `"$RIVET_RUNNER_BIN" architecture init | validate | views`. Агент вызывает их в сессии и видит тот же вывод, что проверка.

Проверка и команды агента Rivet идут в песочнице runner'а. Путь к бинарю приходит в `RIVET_RUNNER_BIN`, а сам файл смонтирован в песочницу только на чтение, даже если лежит под скрытым `$HOME`. Базу проверка забирает с адреса проекта (`-origin`). Без сети она берёт `origin/<ветка>` рабочей копии: перед каждой стадией runner возвращает `.git` к виду свежего клона, поэтому подменённые агентом адрес, refspec или `refs/replace` до проверки не доходят.
