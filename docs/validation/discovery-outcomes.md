# Приёмка исходов исследования

Контракт: OpenSpec store `rivet`, change `add-discovery-decision-outcomes`. Полезный результат отделён от выполнения анализа: `ready` обозначает принятый ответ, `outcome` определяет возможность продолжения разработки.

`backlog_ready` содержит 1–12 Epic, `needs_clarification` содержит 1–5 вопросов без Epic, `no_development_recommended` не создаёт работу. Сохранённый результат неизменяем. Правка бэклога не меняет исход. Store повторно проверяет его под блокировкой при SaveBacklog и ApproveRun, включая вызов старого клиента с `decompose=true`.

Старая корректная история без outcome проецируется без записи обратно. Удалённые исторические материалы не проверяются заново. Невалидная или неизвестная история остаётся доступной для чтения, утверждение закрыто. Новому ответу модели legacy fallback не предоставляется. Сохраняется действующий ранний отказ, если ни в одном материале нет подтверждённых находок: короткий бессодержательный отзыв не считается основанием рекомендации.

## Детерминированные проверки

Из `rivet-service`: `go test ./internal/discovery ./internal/analyst ./internal/store ./internal/api ./cmd/fake-llm`. Store/API suites создают отдельные временные базы. Пропуск по отсутствию PostgreSQL не считается проверкой хранения.

Пять пакетов: `internal/analyst/testdata/outcomes/`. Тест `TestDecisionFixtureSummarySynthesisPipeline` проводит исходный текст через настоящий summary/parser/synthesis/store с фиксированными ответами. Проверяется сохранение контекста в summary, три формы результата, отсутствие созданной работы и отсутствие нового анализа после добавления ответа. Это проверка протокола, она не доказывает качество самостоятельного решения модели.

Источники проверяются по материалам конкретного запуска, строки пересчитываются. Подделанный material_id, чужой материал и отсутствующая цитата дают дефект, затем ограниченный повтор или failed. README и архитектура не превращаются в фиктивные material_id.

## Диагностическая оценка модели

Реальный LLM-прогон не выполнен: модель, доступы и бюджет для него не выбраны. Его нельзя заменять успехом fixture-тестов или включать скрыто как платную проверку.

Для каждого из пяти пакетов зафиксировать модель/connection, версию сервиса, PromptVersion, SHA инструкции и исходных материалов, точные ответы, токены и стоимость. Выполнить один neutral-contract запрос и штатный summary→synthesis pipeline на одинаковых источниках. По каждому ответу оценить: сохранение ограничений, обнаружение блокирующих неизвестных, необходимость разработки, конкретность вопросов, проверяемость источников, полезность результата.

Критические дефекты: выдуманный источник, нарушение явного запрета, разрешение разработки при блокирующей неопределённости. При расхождении baseline/pipeline отдельно проверить summary, trimming/context, parser и только затем инструкцию роли. Один успешный прогон не подтверждает все модели и задачи.

## Проверка на существующем продукте

Выбрать с владельцем brownfield-продукт, оператора и ограниченную доработку плюс баг. До запуска записать ожидаемый полезный результат и критерии готовности. Сравнить Rivet и coding agent с теми же skills на одинаковой принятой версии и источниках.

Для каждого пути сохранить SHA/URL результата, проверенные пользовательские сценарии, содержательные архитектурные артефакты, активное время оператора, число/содержание вмешательств, затраты модели и время ожидания. Ошибки модели, поставки и постановки задачи учитывать отдельно. При отсутствии выбранного продукта/оператора/доступов результат обозначается «не выполнен». Преимущество по бизнес-эффективности пока не доказано.

## Совместимость и откат

Сначала backend reader/guards, затем web и e2e. Старый backend с предположением «каждый ready содержит Epic» нельзя возвращать поверх новых результатов. Безопасный откат сохраняет guards и историю, отключая создание новых исходов. После reconnect UI перечитывает текущую версию. Ответ добавляется новым материалом, затем владелец отдельно запускает анализ. Approve сохраняет Ada gate до планирования и отдельный Start.
