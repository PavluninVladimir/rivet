## Purpose

Определяет жизненный цикл одной задачи: изолированная реализация в ветке, автоматические проверки, независимое review, цикл исправлений и merge. Это конвейер Coding → Tests → Review → Fix → Merge.

## ADDED Requirements

### Requirement: Изоляция работы в ветке и PR

Каждая задача ДОЛЖНА выполняться в отдельной ветке (`agent/task-<N>`). Результат работы ДОЛЖЕН оформляться как PR в целевую ветку репозитория Epic.

#### Scenario: Создание PR

- **WHEN** реализация задачи завершена и автопроверки прошли
- **THEN** система создаёт PR из ветки задачи и переводит задачу в `review`

### Requirement: Автоматические проверки после реализации

После этапа реализации система ДОЛЖНА запускать тесты и прочие автопроверки (сборка, линтеры — согласно настройкам проекта). Провал проверок возвращает задачу на исправление тому же runner'у в рамках текущей попытки.

#### Scenario: Тесты упали

- **WHEN** на этапе `testing` часть тестов провалилась
- **THEN** задача переходит в `fixing`, агент получает результаты тестов, после исправления проверки запускаются повторно

### Requirement: Независимое review

Review ДОЛЖЕН выполнять агент, отличный от агента-исполнителя задачи. Ревьюер получает diff, acceptance criteria и результаты проверок и выносит вердикт: одобрено или список замечаний.

#### Scenario: Review нашло проблемы

- **WHEN** ревьюер вернул замечания
- **THEN** задача переходит в `fixing`, замечания передаются исполнителю, после исправления задача возвращается в `review`; цикл расходует попытку

#### Scenario: Review пройдено

- **WHEN** ревьюер одобрил изменения
- **THEN** задача готова к merge

### Requirement: Merge после успешной проверки

После одобрения review система ДОЛЖНА выполнять merge PR (автоматически или после подтверждения человеком — согласно настройке проекта) и переводить задачу в `done`.

#### Scenario: Автоматический merge

- **WHEN** review пройдено и в настройках включён авто-merge
- **THEN** PR мержится, задача переходит в `done`, зависимые задачи пересчитываются на готовность

### Requirement: Проверка acceptance criteria

Acceptance criteria задачи ДОЛЖНЫ проверяться в ходе конвейера (тестами и/или ревьюером). Если агент не может однозначно интерпретировать критерий, задача ДОЛЖНА переходить в `blocked` с формулировкой вопроса, а не выполняться на основе догадки.

#### Scenario: Неоднозначный критерий

- **WHEN** агент не может определить ожидаемое поведение (например, fail-closed или отдача кэша при недоступности внешней системы)
- **THEN** задача переходит в `blocked` с конкретным вопросом к человеку
