## Контекст

Авторизации нет (dev-заголовок X-Rivet-User); правила автоматики захардкожены в engine. Учётные записи и членство запланированы в `backend/domain-model`; «бот не одобряет себя» — в `backend/scm-integration`. Угроза, специфичная для Rivet: агент, которого политика ограничивает, умеет создавать PR — включая PR, ослабляющий политику.

## Цели / Не-цели

**Цели:** единый policy-слой для действий людей и автоматики; политики как код с аудитом; защита от самоослабления агентом.

**Не-цели:** аутентификация (SSO/OIDC — отдельное изменение, платный тир); замена membership-фильтрации данных policy-движком; UI управления политиками (отдельное изменение rivet-web).

## Решения

- **OPA embedded как Go-библиотека, режим external — опцией.** Sidecar/OPAL/отдельный policy-сервис отвергнуты: у нас нет флота OPA (один rivetd), git-watching делает наш SCM-webhook, канал доставки runner'ам уже есть (gRPC). External-режим закрывает enterprise-сценарий «политиками управляет платформенная команда» и снимает риск компрометации Rivet.
- **Policy-подсистема — модуль с выделяемыми швами**, не отдельный сервис: собственный интерфейс (PolicyEngine, PolicyStore), push через существующие каналы (SSE, gRPC, event log). Вынос в процесс — задокументированная эволюция при появлении второго потребителя политик. NoSQL-хранилище отвергнуто: политика — килобайтный версионируемый документ, форма данных — append-only версии в Postgres (jsonb) или git; вторая система истины не оправдана.
- **Разделение policy vs data (заимствовано из архитектуры OPAL):** отношения (membership) живут в Postgres и применяются в запросах; движок получает атрибуты действия в input и правила — из провайдера. Никакой репликации данных в движок.
- **Метаправила — в коде.** Правило «изменение политики требует человека» принципиально невыразимо самой политикой (агент снял бы его вместе с политикой). Двойной замок для git-провайдера: наша проверка + protected path на хостинге.
- **Модель угроз** (зафиксирована как основа требований): T1 — агент ослабляет политику через PR (guard'ы + доверенный ref + человек-ревьюер); T2 — человек без прав (роль на API политик); T3 — подмена в хранении/доставке (хэш версии, подпись бандлов external, доставка runner'ам от control plane); T4 — тихое изменение (append-only версии + policy.updated + версия в каждом решении).

## Риски / Компромиссы

- [Порог Rego отпугнёт соло-пользователей] → пресеты покрывают базовые случаи без Rego; Rego — опция.
- [Fail-closed останавливает конвейер при ошибке движка] → осознанно: для автоматики безопасность важнее прогресса; эскалация с понятной причиной.
- [Захардкоженные сегодня правила при переносе в политики могут изменить поведение] → пресеты по умолчанию воспроизводят текущие решения (авто-merge выкл, prod кнопкой, ревьюер ≠ исполнитель).

## План миграции

Реализация отдельным изменением: сначала точки принуждения читают пресеты (без Rego), затем embedded OPA и git-провайдер, затем external. Дефолтные пресеты повторяют текущее захардкоженное поведение — миграция незаметна.

## Открытые вопросы

- Точный состав пресетов первой версии (кандидаты: авто-merge, автопубликация по окружениям, обязательный человек для policy-diff — последний не отключаем).
- Формат input для Rego-политик (схема атрибутов действия) — зафиксировать в api-contract реализационного изменения.
