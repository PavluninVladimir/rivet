## Зачем

Сейчас в Rivet нет авторизации (dev-заголовок), а правила поведения автоматики (авто-merge выключен, бот не апрувит себя, prod кнопкой) захардкожены. Спеки уже обещают доступ участникам, приватные сессии и роли, а рынок называет governance автономных агентов незакрытой болью. Нужна единая модель: кто видит данные, кто нажимает кнопки и что разрешено автоматике — c политиками как код и аудитом.

## Что меняется

- Вводится capability `backend/access-policy`: три явных слоя авторизации (данные, действия людей, политики агентов), policy-движок на OPA (embedded по умолчанию, external — enterprise), точки принуждения в API и конвейере.
- Хранение политик — провайдеры с моделью угроз: Postgres (default), git-репозиторий проекта с обязательными guard'ами против самоослабления агентом, external OPA с подписанными бандлами.
- Каждое решение и каждая смена политики фиксируются в event log со ссылкой на версию политики.
- Пресеты политик для базовых случаев без Rego; кастомный Rego и external-режим — граница open-core (согласовано с `backend/monetization`).

## Capabilities

### New Capabilities

- `backend/access-policy`: слои авторизации, policy-движок, точки принуждения, хранение и доставка политик, метаправила, версии и аудит, пресеты.

### Modified Capabilities

Нет — существующие правила (`scm-integration`: бот не одобряет себя; `task-pipeline`: авто-merge по настройке) остаются и получают в новой capability общий механизм исполнения.

## Затронутые репозитории

- [x] `rivet` — движок, хранение, точки принуждения
- [ ] `rivet-web` — управление политиками в консоли (отдельным изменением)
- [ ] `rivet-android`
- [ ] `rivet-ios`

## Impact

- Появляется зависимость на OPA как Go-библиотеку (embedded, без sidecar'ов).
- Захардкоженные правила конвейера станут политиками с пресетами; метаправила защиты политик остаются в коде.
- API управления политиками будет определён в реализационном изменении (это изменение — спецификация).
