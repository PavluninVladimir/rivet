## Purpose

Определяет авторизацию и governance Rivet: три слоя «кто что может» (доступ к данным, действия людей, политики автоматики), policy-движок, безопасное хранение и доставку политик, их версионирование и аудит.

## ADDED Requirements

### Requirement: Три слоя авторизации

Система ДОЛЖНА разделять три слоя: доступ к данным (видимость по членству в проекте — обеспечивается хранилищем данных), действия людей (право на мутации: merge, ответы на эскалации, управление runner'ами и политиками) и политики автоматики (что разрешено планировщику, агентам и публикациям). Политики автоматики НЕ ДОЛЖНЫ использоваться для вычисления видимости данных.

#### Scenario: Слои не смешиваются

- **WHEN** участник запрашивает список задач
- **THEN** видимость определяется членством в проектах на уровне запросов к хранилищу, без обращения к policy-движку

### Requirement: Policy-движок с двумя режимами

Система ДОЛЖНА оценивать политики через движок OPA: по умолчанию — встроенный (в процессе control plane, без отдельных служб); в режиме external — запросами к внешнему OPA-endpoint'у, управляемому вне Rivet. Режим настраивается на установку; интерфейс точек принуждения от режима не зависит.

#### Scenario: Внешний контур политик

- **WHEN** установка настроена на external-режим с адресом корпоративного OPA
- **THEN** все решения политик автоматики запрашиваются у внешнего движка, а локальное управление политиками отключено

### Requirement: Точки принуждения

Политики ДОЛЖНЫ применяться: к мутациям API от людей (merge, управление Epic и runner'ами, изменение политик), к гейтам конвейера (авто-merge, автопубликация, назначение задач) и к публикациям в окружения. Для действий автоматики отказ движка ДОЛЖЕН трактоваться как запрет (fail-closed); для чтения данных людьми движок не участвует, для мутаций людей отказ движка — запрет.

#### Scenario: Политика запрещает авто-merge в prod-репозиторий

- **WHEN** review задачи пройден, авто-merge включён, но политика проекта требует человека для этого репозитория
- **THEN** merge не выполняется автоматически, задача ждёт подтверждения, в event log — «merge отложен политикой <версия>»

#### Scenario: Движок недоступен

- **WHEN** оценка политики невозможна (ошибка движка)
- **THEN** действия автоматики приостанавливаются (fail-closed) с эскалацией, чтение данных людьми продолжает работать

### Requirement: Хранение политик — провайдеры и модель угроз

Система ДОЛЖНА поддерживать провайдеры хранения политик: (1) собственное хранилище (по умолчанию) — версии append-only, изменение только людьми с соответствующим правом через API, у агентов нет пути записи; (2) git-репозиторий проекта — политика как код, только при включённых guard'ах из требования о самоослаблении; (3) external — политики вне Rivet, при доставке бандлами ДОЛЖНА проверяться подпись.

#### Scenario: Агент не может изменить политику через API

- **WHEN** сессия агента пытается обратиться к API управления политиками
- **THEN** запрос отклоняется: субъекты-автоматика не имеют права записи политик независимо от содержимого политик

### Requirement: Защита от самоослабления (метаправила в коде)

Правила защиты политик ДОЛЖНЫ быть реализованы в коде системы и НЕ ДОЛЖНЫ быть выразимы или отключаемы самими политиками: политика читается только из доверенного ref (основная ветка после человеческого merge, никогда из рабочей ветки задачи); PR, изменяющий файлы политики, никогда не проходит авто-merge и требует ревьюера-человека (review-агента недостаточно); система проверяет защиту пути политики на хостинге до включения git-провайдера.

#### Scenario: Агент приносит ослабленную политику в PR

- **WHEN** PR задачи содержит изменение файла политики, а review-агент одобрил PR
- **THEN** авто-merge блокируется метаправилом, создаётся эскалация «изменение политики требует человека», действующей остаётся политика из доверенного ref

### Requirement: Версионирование и аудит решений

Каждая активация версии политики ДОЛЖНА фиксироваться событием в event log с идентификатором версии (хэш/git-sha). Каждое решение точки принуждения ДОЛЖНО ссылаться на версию политики, по которой принято. История версий append-only.

#### Scenario: Воспроизводимый аудит

- **WHEN** аудитор спрашивает, почему действие месяц назад было разрешено
- **THEN** событие решения содержит версию политики, и её текст восстановим из истории версий

### Requirement: Доставка политик runner'ам

Политики, применяемые на стороне runner'а, ДОЛЖНЫ доставляться по протоколу агентов вместе с назначением, с хэшем версии; runner ДОЛЖЕН применять только версию, подтверждённую control plane, и НЕ ДОЛЖЕН читать политику из рабочей копии репозитория.

#### Scenario: Подмена политики в рабочей копии

- **WHEN** в рабочей копии репозитория на машине runner'а файл политики изменён
- **THEN** runner продолжает применять версию, полученную от control plane, а расхождение не влияет на исполнение

### Requirement: Пресеты вместо обязательного Rego

Базовые политики ДОЛЖНЫ настраиваться пресетами (переключатели: авто-merge, автопубликация по окружениям, обязательность ревьюера-человека) без написания Rego; пресеты компилируются в стандартные политики с теми же версионированием и аудитом. Кастомные Rego-политики и external-режим относятся к платным возможностям (граница open-core — `backend/monetization`).

#### Scenario: Соло-пользователь включает авто-merge

- **WHEN** пользователь включает пресет «авто-merge после review» для проекта без prod-окружения
- **THEN** создаётся новая версия стандартной политики с событием в event log, Rego писать не требуется
