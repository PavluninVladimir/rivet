## Goals / Non-Goals

**Goals:**

- Зафиксировать поведение системы на уровне, достаточном для последующей декомпозиции на инженерные изменения (архитектура, MVP).
- Сохранить главный принцип во всех спеках: детерминированный control plane, модель — только внутри задачи.
- Извлечь из прототипа все продуктовые решения, чтобы прототип перестал быть единственным носителем знаний.

**Non-Goals:**

- Выбор стека, архитектуры и протоколов (runner API, транспорт, хранилище) — предмет следующего изменения.
- Требования к масштабированию и мультитенантности — за рамками первой итерации; из прав доступа в scope только базовые учётные записи и членство в проекте (без них нет командной видимости), роли и SSO — позже, в платном тире.
- Пиксельная спецификация UI — эталоном остаётся прототип, текстом фиксируется только состав и поведение.

## Decisions

- **Разрез на 8 capabilities** (`domain-model`, `epic-decomposition`, `orchestration`, `task-pipeline`, `runners`, `human-escalation`, `observability`, `console`): по осям «словарь → планирование → исполнение → люди → наблюдаемость → интерфейс». Альтернатива — одна большая спека «оркестратор» — отвергнута: изменения в жизненном цикле задачи и в планировщике будут эволюционировать независимо.
- **Статусные модели берутся из прототипа как есть** (9 статусов задачи, 5 статусов runner'а). Альтернатива — упростить до 4–5 статусов — отвергнута: прототип показал, что различие `ready`/`queued` и `fixing`/`running` несёт управленческий смысл (причины ожидания, расход попыток).
- **Console — отдельная capability со ссылкой на прототип**, а не текстовый пересказ вёрстки: требования фиксируют состав представлений и ключевые взаимодействия, эталон остаётся в HTML. Так спеки не устаревают при правках дизайна.
- **DAG ограничен рамками одного Epic.** Межэпиковые зависимости в требования не включены — это резко упрощает планировщик MVP; при необходимости появятся отдельным изменением.
- **Язык артефактов — русский**, нормативное слово — «ДОЛЖЕН» (эквивалент SHALL), структура требований — формат OpenSpec (Requirement / Scenario, WHEN/THEN).
- **Интеграция агентов: протокол в центре, адаптеры по краям.** Вместо N интеграций «Rivet ↔ агент» фиксируется один протокол (регистрация, события/транскрипт, usage, heartbeat), а способы подключения — адаптеры разной глубины данных: нативный плагин, универсальная CLI-обёртка, сессия из интерфейса Rivet. Альтернатива «только плагины под каждого агента» отвергнута: вечная гонка за версиями N агентов; альтернатива «работа только через интерфейс Rivet» отвергнута: требует смены привычного инструмента и убивает adoption.
- **Сессия — общая сущность.** Runner оркестратора и интерактивная работа человека с агентом сведены к одной сущности «сессия» с разным водителем (планировщик / пользователь). Один транспорт, один формат событий, один механизм live-стриминга; командная видимость и наблюдаемость оркестратора не дублируют друг друга.
- **SCM и деплой — адаптеры, как и агенты.** Единый протокол SCM-адаптера (GitHub / GitLab / Gitea) и адаптеры доставки. Rivet не строит собственную CI/CD-систему (там ArgoCD/Flux и зрелые пайплайны), но ОБЯЗАН уметь деплоить сам в простых случаях (SSH + compose, Kubernetes) — иначе соло-сегмент без CI не получает замкнутого цикла. Альтернатива «merge = done, дальше не наше дело» отвергнута: рвётся связка разработка → эксплуатация.
- **Работа в закрытых периметрах — через runner.** Git-операции и деплой для недоступных снаружи GitLab/окружений выполняет runner внутри периметра; control plane оперирует метаданными. Это одно решение сразу для корпоративного self-hosted GitLab и для прод-окружений за VPN.

## Итоги ревизии (задачи 1.1, 3.1, 3.2)

Владелец продукта принял все требования без изменений (ревизия 1.1 закрыта). MVP-срез решено **не выделять**: реализуется весь объём требований, порядок работ задаётся архитектурой и зависимостями, а не отсечением функций. Сценарий первой демонстрации: один Epic на реальном репозитории, 2–3 runner'а (нативный плагин + универсальная обёртка), полный цикл задачи с одной эскалацией и публикацией в staging — требований для него достаточно.

## Сверка с дизайн-прототипом (итог задачи 1.2)

Все представления и поведение прототипа сверены со спеками. Найденные при сверке пробелы устранены правками `backend/domain-model`: статусная модель Epic, атрибут «оценка трудоёмкости» задачи (взвешенный прогресс «weighted by estimate» из прототипа), статус `cancelled` с полной матрицей переходов. Осознанно исключено из требований (остаётся деталями прототипа/реализации): бейдж окружения инстанса «PROD» в сайдбаре, конкретные цвета и типографика (источник — прототип как эталон), содержимое демо-данных, точный набор переключателей Settings (определится составом реализованных функций).

## Risks / Trade-offs

- [Спеки разойдутся с прототипом при доработке дизайна] → правило в спеке `console`: отклонения фиксируются в design-документах изменений; прототип и спеки правятся одним изменением.
- [Требования писались от прототипа, а прототип — витрина, не полный продукт] → в tasks.md заложена ревизия требований человеком (владельцем продукта) до синка в основные спеки.
- [Слишком ранняя фиксация деталей (пороги, лимиты) свяжет руки при реализации] → числовые значения в спеках даны как примеры/настройки, не как константы.
- [Восемь спек создают ощущение полноты, хотя часть тем не покрыта (авторизация, мультирепо-Epic, стоимость review-агентов)] → непокрытые темы перечислены явно в Non-Goals и Open Questions.

## Open Questions

Решено владельцем продукта и внесено в спеки (задача 2.1): лимит попыток — 3 по умолчанию; авто-merge по умолчанию выключен (включается настройкой проекта); вмешательство человека полностью сбрасывает счётчик попыток; единица тарификации — нормированная единица работы runner'а; при `offline` runner'а попытка перезапускается с нуля; отдельный профиль ревьюера не нужен (любой runner с capability `review`); автопубликации коалесцируются. Вопросы секретов деплоя и партиционирования event log перенесены в `define-rivet-architecture`.

Остаются открытыми (безопасно решить при реализации):

- Числовые настройки: порог «горячего» контекста runner'а (ориентир 60 % из прототипа), таймаут heartbeat до `offline`.
- Правила автоматического маскирования секретов в транскриптах: набор детекторов и допустимый уровень ложных срабатываний.
- Порядок реализации обратного канала по адаптерам: сначала контекст задачи и предупреждения о пересечениях, знания проекта — вместе со слоем памяти.
