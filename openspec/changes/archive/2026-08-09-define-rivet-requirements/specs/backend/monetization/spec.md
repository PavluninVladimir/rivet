## Purpose

Определяет, как система зарабатывает: метеринг использования, тарифные планы по гибридной модели «подписка + использование», BYOK-принцип (инференс не перепродаётся), платные управляемые runner'ы и прозрачность затрат для пользователя.

## ADDED Requirements

### Requirement: Метеринг использования как основа биллинга

Система ДОЛЖНА вести биллинг-качества учёт использования, выводимый из event log: выполненные задачи (в т.ч. доведённые до merge), время работы runner'ов, израсходованные токены по моделям. Записи метеринга ДОЛЖНЫ быть идемпотентными (повторная обработка события не удваивает счёт) и сверяемыми с event log.

#### Scenario: Сверка счёта

- **WHEN** пользователь открывает детализацию счёта за период
- **THEN** каждая строка счёта раскрывается до конкретных задач и событий, из которых она посчитана

### Requirement: Гибридная тарифная модель

Система ДОЛЖНА поддерживать планы вида «базовая подписка + включённый объём использования + оплата сверх объёма» (единица тарификации — нормированная единица работы runner'а; доведённые до merge задачи — отчётная метрика, не тарифная). Система ДОЛЖНА показывать остаток включённого объёма и предупреждать пользователя до его исчерпания.

#### Scenario: Предупреждение о расходе объёма

- **WHEN** израсходовано 80 % включённого в план объёма
- **THEN** пользователь получает уведомление с прогнозом, на сколько хватит остатка при текущем темпе

#### Scenario: Превышение включённого объёма

- **WHEN** объём плана исчерпан
- **THEN** дальнейшее использование тарифицируется по ставке сверх объёма согласно плану, либо — если пользователь включил жёсткий лимит — новые задачи ставятся в очередь до подтверждения

### Requirement: BYOK — инференс не тарифицируется платформой

Пользователь ДОЛЖЕН иметь возможность подключать собственные ключи и подписки агентов/моделей (Claude Code, Codex и др.). Расход по ключам пользователя оплачивается им напрямую провайдеру; платформа НЕ ДОЛЖНА добавлять наценку на такой инференс и ДОЛЖНА учитывать его в отчётах как справочную стоимость.

#### Scenario: Работа на своих ключах

- **WHEN** все runner'ы пользователя используют его собственные ключи
- **THEN** счёт платформы содержит только подписку и платные функции платформы, а стоимость инференса отображается в usage-отчётах как справочная

### Requirement: Управляемые облачные runner'ы

Система МОЖЕТ предлагать платные управляемые runner'ы (облачная песочница с предустановленным агентом) как альтернативу собственным. Их тарификация ДОЛЖНА вестись по нормированным единицам работы с публичной ставкой плана; пользователь ДОЛЖЕН видеть цену до запуска задачи на таком runner'е.

#### Scenario: Выбор управляемого runner'а

- **WHEN** пользователь добавляет управляемый runner
- **THEN** система показывает ставку за единицу работы и включает его расход в биллинг платформы

### Requirement: Границы бесплатного и платного (open-core)

Ядро системы (оркестрация, конвейер задач, консоль, self-hosted-развёртывание) ДОЛЖНО быть доступно бесплатно. Платными ДОЛЖНЫ быть функции масштаба и организации: портфель проектов, командные роли и SSO, централизованный биллинг по организациям, управляемые runner'ы, расширенная аналитика экономии. Система ДОЛЖНА применять ограничения активного плана и явно показывать, какая функция требует более высокого плана.

#### Scenario: Функция недоступна на плане

- **WHEN** пользователь на бесплатном плане открывает платную функцию (например, портфель организаций)
- **THEN** система показывает, каким планом функция открывается, не блокируя остальную работу

### Requirement: Прозрачность затрат до запуска

Перед запуском Epic система ДОЛЖНА показывать оценку стоимости (диапазон: токены/единицы работы по плану декомпозиции) и ДОЛЖНА позволять задать бюджет Epic; фактическая стоимость сравнивается с оценкой в usage-отчётах.

#### Scenario: Оценка перед стартом

- **WHEN** пользователь просматривает план Epic перед запуском
- **THEN** он видит оценку стоимости выполнения и может установить бюджетный лимит Epic
