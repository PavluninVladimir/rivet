## Purpose

Определяет публикацию результатов разработки: окружения как сущность, этапы Deploy → Verify после merge, собственная способность системы деплоить (Linux-хост, Kubernetes) и дирижирование внешними CI/CD и GitOps, режимы запуска и реакция на провал.

## ADDED Requirements

### Requirement: Окружение как сущность

Проект ДОЛЖЕН иметь настраиваемые окружения публикации: имя (например, staging, prod), тип исполнения (собственный деплой на Linux-хост, собственный деплой в Kubernetes, внешний CI/CD, GitOps), правило запуска и статус последней публикации (версия, время, результат).

#### Scenario: Окружения проекта

- **WHEN** пользователь открывает проект
- **THEN** он видит список окружений с версией, временем и результатом последней публикации в каждом

### Requirement: Этапы Deploy и Verify

Публикация ДОЛЖНА состоять из этапа доставки (Deploy) и обязательного этапа проверки (Verify: health-check и/или smoke-проверки окружения). Публикация считается успешной только после Verify; все этапы пишутся в event log, расход деплой-runner'ов учитывается в usage.

#### Scenario: Успешная публикация

- **WHEN** деплой в staging завершился и health-check прошёл
- **THEN** окружение staging показывает новую версию как текущую, а в event log есть события deploy и verify

### Requirement: Собственная способность деплоить

Система ДОЛЖНА уметь публиковать без внешнего CI/CD: на Linux-хост (по SSH, включая docker compose) и в Kubernetes-кластер (манифесты/helm). Деплой выполняется runner'ом с capability `deploy`; для окружений в закрытом периметре — runner'ом внутри периметра.

#### Scenario: Публикация без внешнего CI

- **WHEN** проект без настроенного CI/CD запускает публикацию в окружение типа «Linux-хост»
- **THEN** деплой-runner доставляет новую версию по SSH, выполняет Verify и фиксирует результат

### Requirement: Дирижирование внешними системами доставки

Система ДОЛЖНА поддерживать окружения, где доставку выполняет внешняя система: триггер пайплайна CI/CD (GitLab CI, GitHub Actions) или GitOps-обновление (изменение манифестов с ожиданием синхронизации). Система запускает процесс, наблюдает его ход и забирает результат как свой этап Deploy.

#### Scenario: Публикация через GitLab CI

- **WHEN** окружение настроено на внешний пайплайн и запущена публикация
- **THEN** система триггерит пайплайн, ждёт его завершения, отражает ход в event log и выполняет Verify после успеха

### Requirement: Режимы запуска публикации

Правило запуска ДОЛЖНО настраиваться на каждое окружение: автоматически (после merge изменений; накопившиеся за время текущей публикации merge'и коалесцируются в одну следующую) или вручную (публикацию запускает участник). Оба режима ДОЛЖНЫ работать одновременно в одном проекте (например, staging — автоматически, prod — кнопкой).

#### Scenario: Staging автоматом, prod кнопкой

- **WHEN** задача смержена в проекте, где staging настроен на автозапуск, а prod — на ручной
- **THEN** публикация в staging запускается сама, а prod ожидает явного запуска участником

### Requirement: Провал публикации

При провале Deploy или Verify система ДОЛЖНА: для собственных деплоев — откатить окружение к предыдущей успешной версии, остановить последующие автопубликации в это окружение и создать эскалацию с контекстом провала. Провал публикации ДОЛЖЕН порождать сигнал для создания фикс-задачи.

#### Scenario: Health-check провалился

- **WHEN** после деплоя в staging health-check не прошёл
- **THEN** окружение откатывается к предыдущей версии, публикации в staging приостанавливаются, в needs attention появляется эскалация с логами провала
