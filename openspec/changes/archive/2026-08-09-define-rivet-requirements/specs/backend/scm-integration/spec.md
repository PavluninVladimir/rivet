## Purpose

Определяет интеграцию с git-хостингами через единый протокол SCM-адаптера: операции с ветками и PR/MR, статусы проверок, webhooks, идентичность бота и работа с self-hosted инстансами, в том числе в закрытых периметрах.

## ADDED Requirements

### Requirement: Протокол SCM-адаптера

Система ДОЛЖНА определять единый интерфейс работы с git-хостингом: создание ветки, создание PR/MR и чтение его diff, чтение статусов проверок (CI), выполнение merge, подписка на события хостинга. Конвейер задач НЕ ДОЛЖЕН зависеть от конкретного хостинга — различия PR/MR и API скрывает адаптер.

#### Scenario: Конвейер поверх разных хостингов

- **WHEN** два проекта подключены к разным хостингам (например, GitHub и GitLab)
- **THEN** задачи обоих проектов проходят одинаковый конвейер (ветка → PR/MR → проверки → merge) без различий в поведении системы

### Requirement: Первая волна адаптеров

Система ДОЛЖНА предоставлять адаптеры для GitHub, GitLab (облачный и self-hosted, с указанием URL инстанса и токенами на каждый инстанс) и Gitea/Forgejo.

#### Scenario: Подключение self-hosted GitLab

- **WHEN** пользователь подключает проект к self-hosted GitLab, указав URL инстанса и токен
- **THEN** система работает с этим инстансом наравне с облачными хостингами: ветки, MR, статусы пайплайнов, merge

### Requirement: Идентичность бота

Операции системы на хостинге ДОЛЖНЫ выполняться от отдельной бот-идентичности (например, `rivet-bot`), а не от личного токена участника. Система НЕ ДОЛЖНА одобрять собственные PR/MR от той же идентичности, если правила репозитория требуют независимого одобрения.

#### Scenario: Атрибуция изменений

- **WHEN** оркестратор создаёт PR по задаче
- **THEN** автором PR на хостинге значится бот-идентичность системы, а связь с задачей и водителем видна в описании PR и в event log

### Requirement: Git-операции с runner'а

Для хостингов, недоступных из control plane (закрытый периметр, VPN), git-операции ДОЛЖНЫ выполняться runner'ом, находящимся внутри периметра; control plane оперирует только метаданными.

#### Scenario: GitLab за VPN

- **WHEN** проект подключён к GitLab-инстансу, доступному только из внутренней сети, где работает runner
- **THEN** клонирование, ветки, push и MR выполняются runner'ом, и конвейер работает полностью, хотя control plane не имеет прямого доступа к инстансу

### Requirement: События хостинга в конвейере

Система ДОЛЖНА принимать события хостинга (завершение CI-проверок, merge, закрытие PR, комментарии ревьюеров-людей) и отражать их в event log и в конвейере соответствующих задач.

#### Scenario: Человек смержил вручную

- **WHEN** участник вручную мержит PR задачи на хостинге
- **THEN** система получает событие, переводит задачу в `done`, пересчитывает готовность зависимых задач и фиксирует событие в event log
