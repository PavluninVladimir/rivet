## Purpose

Определяет детерминированный планировщик Rivet: запуск готовых задач на подходящих runner'ах, параллельность, retry, лимиты попыток и реакцию на сбои. Главный принцип: модель решает задачу, Rivet управляет процессом — переходы контролирует код, а не промпт.

## ADDED Requirements

### Requirement: Детерминированное управление процессом

Переходы между этапами, проверки, retry, зависимости и блокировки ДОЛЖНЫ контролироваться детерминированным кодом оркестратора. Workflow НЕ ДОЛЖЕН храниться в промпте агента; агент получает только контекст своей задачи.

#### Scenario: Агент не управляет процессом

- **WHEN** агент в своём выводе «объявляет» задачу завершённой
- **THEN** статус задачи меняется только после того, как оркестратор сам проверил результат этапа (тесты, review)

### Requirement: Параллельный запуск независимых задач

Оркестратор ДОЛЖЕН запускать все задачи в статусе `ready` параллельно, пока есть свободные runner'ы с подходящими capabilities.

#### Scenario: Две независимые задачи

- **WHEN** две задачи без взаимных зависимостей находятся в `ready` и свободны два подходящих runner'а
- **THEN** обе задачи запускаются одновременно на разных runner'ах

### Requirement: Подбор runner'а по capabilities

Задача ДОЛЖНА назначаться только на runner, обладающий всеми требуемыми capabilities. Если подходящего свободного runner'а нет, задача ДОЛЖНА оставаться в `ready` с явной причиной ожидания.

#### Scenario: Нет runner'а с нужной capability

- **WHEN** задача требует capability `frontend`, а свободных runner'ов с ней нет
- **THEN** задача остаётся в `ready` с причиной вида «No free runner with capability "frontend"» и назначается, как только такой runner освобождается

### Requirement: Лимит попыток

Каждая задача ДОЛЖНА иметь лимит попыток; значение по умолчанию — 3, настраивается на проект и на задачу. Неудачный цикл исправления (провал тестов или review) расходует попытку. При исчерпании лимита задача ДОЛЖНА переходить в `failed` и эскалироваться человеку; новые автоматические попытки НЕ ДОЛЖНЫ запускаться.

#### Scenario: Исчерпание лимита review

- **WHEN** review отклоняет результат в третий раз при лимите «3»
- **THEN** задача переходит в `failed` с причиной «Review failed 3 times — attempt limit reached» и попадает в очередь эскалаций

### Requirement: Сбой зависимости блокирует потомков

Если задача перешла в `failed`, все транзитивно зависящие от неё незавершённые задачи ДОЛЖНЫ переходить в `blocked` с указанием отказавшей зависимости.

#### Scenario: Потомок заблокирован

- **WHEN** задача A перешла в `failed`, а задача B зависит от A
- **THEN** B переходит в `blocked` с причиной «Dependency A failed»

### Requirement: Пауза и возобновление Epic

Пользователь ДОЛЖЕН иметь возможность поставить Epic на паузу и возобновить его. При паузе новые задачи не запускаются, а работающие runner'ы корректно завершают текущий шаг.

#### Scenario: Пауза Epic

- **WHEN** пользователь нажимает «Pause Epic»
- **THEN** планирование новых задач останавливается, идущие шаги дорабатывают до безопасной точки, состояние Epic сохраняется для возобновления
