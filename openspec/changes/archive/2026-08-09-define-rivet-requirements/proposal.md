## Why

Rivet сейчас существует в виде видения (CLAUDE.md) и дизайн-прототипа консоли (`agent-orchestration-console.html`). Прежде чем писать код, нужно превратить видение и дизайн в проверяемые требования: зафиксировать доменную модель, правила оркестрации, жизненный цикл задачи и точки участия человека. Без этого декомпозиция на инженерные эпики будет произвольной, а прототип останется единственным носителем знаний о продукте.

## What Changes

- Из дизайн-прототипа и видения извлекается и фиксируется доменная модель: Project → Epic → Task, DAG зависимостей, статусная модель задач и runner'ов.
- Формулируются требования к оркестрации: декомпозиция Epic на задачи, планирование по DAG, подбор runner'а по capabilities, retry и лимиты попыток.
- Фиксируется конвейер задачи Coding → Tests → Review → Fix → Merge с независимым review-агентом.
- Описываются правила эскалации человеку (needs attention): когда Rivet останавливается и ждёт решения.
- Формулируются требования к наблюдаемости: event log всех действий и учёт usage (токены, стоимость).
- Фиксируются требования к консоли управления на основе прототипа.
- Фиксируется модель монетизации: метеринг, гибридные тарифы, BYOK, управляемые runner'ы, open-core.
- Вводится единый протокол подключения внешних агентов и понятие сессии (интерактивной и оркестрированной); в доменную модель добавляются пользователи и членство в проектах.
- Формулируется командная видимость: сессии и запросы участников видны команде, эскалации назначаются.
- Прорабатывается подключение git-хостингов (GitHub, GitLab включая self-hosted, Gitea/Forgejo) через единый SCM-адаптер и бот-идентичность.
- Конвейер продлевается за merge: публикация в окружения (Linux-хост, Kubernetes, внешние CI/CD и GitOps) с обязательной проверкой и откатом.
- Составляется план работ по доводке требований: открытые вопросы, приоритизация MVP, критерии готовности спецификаций.

Кода это изменение не затрагивает — результатом являются спецификации в `openspec/specs/` и план их доводки.

## Capabilities

### New Capabilities

- `backend/domain-model`: сущности Project, Epic, Task, Runner; DAG зависимостей; статусные модели и допустимые переходы.
- `backend/epic-decomposition`: декомпозиция Epic на небольшие задачи с зависимостями и acceptance criteria; построение DAG; пересмотр плана человеком до запуска.
- `backend/orchestration`: детерминированный планировщик — готовность задач, параллельный запуск независимых задач, подбор runner'а по capabilities, retry, лимиты попыток, реакция на сбои зависимостей.
- `backend/task-pipeline`: жизненный цикл одной задачи — реализация, тесты и автопроверки, независимое review, возврат на исправление, merge; изоляция в ветке `agent/task-N` и PR.
- `backend/runners`: реестр исполнителей — агент, модель, хост, capabilities, статусы, контроль контекста; подключение и отключение runner'ов.
- `backend/human-escalation`: очередь «needs attention» — причины эскалаций (blocked, review limit, test failed, нехватка информации), действия человека и возврат задачи в работу.
- `backend/observability`: event log всех действий (кто, что, когда, в рамках чего) и учёт usage — токены и стоимость в разрезе Epic / задачи / runner'а.
- `clients/web-console`: консоль управления — представления Projects, Epics (DAG и список), Tasks, Runners, Activity, Usage, деталка задачи, командная палитра; эталон — дизайн-прототип.
- `clients/mobile`: мобильные клиенты (Android, iOS) — паритет состояния с консолью, push-уведомления об эскалациях, действия с телефона (разблокировка, управление Epic, ручная публикация, короткая сессия), наблюдение за live-работой.
- `backend/monetization`: модель заработка — биллинг-метеринг поверх event log, гибридные тарифы «подписка + использование», BYOK без наценки на инференс, платные управляемые runner'ы, границы open-core, прозрачность затрат до запуска Epic.
- `backend/agent-integration`: единый протокол подключения внешних агентов (общий для runner'ов и интерактивных сессий), уровни глубины данных, адаптеры — нативный плагин / универсальная CLI-обёртка / сессия из интерфейса Rivet, открытый SDK, обратный канал контекста.
- `backend/team-visibility`: командная видимость — реестр активных сессий проекта, история запросов с поиском, приватность и маскирование секретов, предупреждения о пересечениях работ, взятие эскалаций в работу.
- `backend/scm-integration`: единый протокол SCM-адаптера (ветки, PR/MR, статусы проверок, merge, события хостинга); адаптеры GitHub, GitLab (включая self-hosted) и Gitea/Forgejo; бот-идентичность; git-операции с runner'а для закрытых периметров.
- `backend/deployment`: публикация — окружения как сущность, этапы Deploy → Verify, собственный деплой (Linux-хост по SSH, Kubernetes) и дирижирование внешними CI/CD и GitOps, режимы «автоматически/кнопкой» на окружение, откат и эскалация при провале.

### Modified Capabilities

Нет — существующих спецификаций в проекте пока нет.

## Impact

- Появляются первые спецификации в `openspec/specs/` (через delta-спеки этого изменения) — они становятся источником истины вместо неявных знаний в прототипе.
- `agent-orchestration-console.html` получает статус эталона UX, на который ссылаются требования `clients/web-console`.
- Кодовая база, API и зависимости не затрагиваются; изменение готовит почву для последующих инженерных изменений (архитектура, MVP).
