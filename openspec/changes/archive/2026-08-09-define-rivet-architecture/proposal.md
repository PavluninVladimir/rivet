## Зачем

Требования (`define-rivet-requirements`, 14 capabilities) описывают, ЧТО делает система, но архитектурные решения — хранилища, транспорт, связь с runner'ами — пока живут только в обсуждениях. Их нужно зафиксировать до первого кода: выбор баз данных определяет форму control plane, биллинга и live-стриминга.

## Что меняется

- Фиксируются решения по хранилищам: PostgreSQL как единая система записи (состояние, event log, очередь планировщика, usage), объектное хранилище для тяжёлых артефактов, pgvector для будущего слоя памяти.
- Фиксируются отвергнутые альтернативы с причинами (SQLite, выделенный брокер, отдельный event store, отдельная векторная БД).
- Фиксируется транспорт: gRPC bidi-stream с исходящим соединением от runner'а; клиентам — HTTP/JSON + SSE; структура Go-репозитория — один модуль, три бинарника (`rivetd`, `rivet-runner`, `rivet`).
- Определяется api-contract v1 и план вертикального среза: одна задача проходит полный цикл queued → … → merge на GitHub с review вторым runner'ом и эскалациями, наблюдаемая через API/SSE.
- Поведение системы не меняется относительно требований — все поведенческие контракты в `openspec/specs/`; изменение их реализует, а не расширяет.

## Impact

- Кода ещё нет — изменение задаёт основу для первых инженерных задач бэкенда.
- Решения по базам станут ограничениями для всех последующих изменений (метеринг — поверх event log в Postgres; транскрипты — в объектном хранилище).
- Открытые архитектурные вопросы (связь runner ↔ control plane, секреты деплоя, SQLite для соло-сегмента) собраны здесь как повестка следующих проработок.
