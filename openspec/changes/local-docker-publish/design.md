# local-docker-publish — дизайн

## Контекст

Окружение публикации (`domain.Environment`) хранит `exec_type`, правило
запуска, JSON-конфигурацию, список capabilities runner'а и флаг паузы.
Деплой-конвейер уже даёт: очередь с partial unique индексами «одна queued» и
«одна активная» на окружение, CAS-переходы статусов
(`queued → deploying → verifying → done|failed|rolled_back`), watchdog,
откат на предыдущую успешную версию, эскалацию при провале и сохранение
лога в blob.

Локальная Docker-публикация встраивается в этот конвейер, а не заводит
второй. Своё у неё — конфигурация, сборка образа, запуск контейнера на
loopback и сверка состояния с Docker.

## Решения

### 1. Отдельный `exec_type = local_docker`, а не режим `ssh`

`deploy_cmd` — произвольный shell, и вся типовая локальная публикация
сегодня живёт в нём. Пока команда остаётся полем формы, платформа ничего
не контролирует: ни адрес, ни порт, ни запуск.

Поэтому локальная публикация — свой тип окружения со своей моделью
конфигурации. Команды в нём нет вообще. Список допустимых типов
расширяется до `ssh | k8s | pipeline | gitops | local_docker`, остальные
типы не меняются.

Модель: `LocalDockerEnvironmentConfig` в `config.local_docker`.

```json
{
  "container_port": 8080,
  "health_path": "/healthz",
  "recipe": "auto",
  "build_context": ".",
  "startup_timeout_s": 120,
  "stop_timeout_s": 10,
  "env": {"APP_MODE": "local"}
}
```

`port`, `deploy_cmd`, `verify_cmd`, `verify_url`, `host` в конфигурации
`local_docker` нет: адрес и проверка — забота платформы.

### 2. Loopback — инвариант платформы, а не настройка

Порт публикации выдаёт платформа: на хосте runner'а ищется свободный порт в
диапазоне 20000–29999, контейнер запускается с
`-p 127.0.0.1:<port>:<container_port>`.

После запуска runner проверяет `docker inspect`: `HostIp` каждого
опубликованного порта обязан быть `127.0.0.1` или `::1`. Пустой `HostIp`
означает `0.0.0.0` — это нарушение, контейнер немедленно останавливается,
публикация проваливается с кодом `loopback_not_bound`.

Проверка после запуска нужна потому, что «правильный флаг» — не гарантия:
пользователь может подменить конфигурацию Docker-демона
(`userland-proxy`, `default-address-pools`), а сетевой режим контейнера
влияет на итоговые привязки.

`--network host`, `macvlan`, `container:<id>` запрещены: в этих режимах
loopback-привязки порта нет.

### 3. Blue-green на loopback вместо остановки старого контейнера

Redeploy не должен ронять работающую версию из-за сломанной сборки. Новое
поколение публикации поднимается на свободном порту рядом со старым,
проходит healthcheck, и только после успеха старый контейнер получает
SIGTERM (и SIGKILL через `stop_timeout_s`).

Плата — `listen` меняется между поколениями. Статус публикации всегда
отдаёт актуальный адрес, UI показывает его рядом с версией. Потребители,
которым нужен неизменный номер порта, — открытый вопрос ниже.

### 4. Рецепты сборки — код платформы, не текст от пользователя

Dockerfile генерируется во временном каталоге runner'а, в репозиторий не
пишется. Рецепт выбирается по маркерам в рабочей копии версии публикации:

- `go` — есть `go.mod`; точка входа ищется по порядку: единственный
  каталог `cmd/*`, затем `./`, затем `main.go`; сборка многостадийная,
  базовые образы закреплены digest'ом;
- `node` — есть `package.json`; `npm ci`, затем `npm run build`, если
  скрипт объявлен, запуск `npm start`;
- `static` — есть `index.html` в корне `build_context`; файлы отдаёт
  встроенный в образ сервер платформы с готовой конфигурацией.

`recipe: auto` включает автоопределение в этом же порядке. Маркеров нет —
провал `recipe_not_detected` с текстом, какой файл добавить. Аргументы
сборки, `build-args` и секреты в сборку не передаются.

### 5. Healthcheck — на runner'е, не в control plane

Control plane по умолчанию не ходит на loopback, частные и служебные
адреса: фильтр `URLPolicy` закрывает SSRF. Ослаблять его ради локальной
публикации нельзя — это открыло бы все внутренние адреса установки.

Поэтому healthcheck выполняет runner из сети своего хоста: HTTP GET
`http://127.0.0.1:<port><health_path>`, успех — код 200–399, таймаут 2 с,
тело читается не больше 4 КиБ и не сохраняется. Redirect не отслеживается:
иначе проверка ушла бы с loopback.

Периодический контроль после публикации — обычное наблюдение окружения
(`operations`): `monitor.check_url` платформа заполняет сама из `listen`,
проверка идёт с сети runner'а, как у окружений с собственной доставкой.
`monitor.check_cmd` и `monitor.logs_cmd` для `local_docker` запрещены.

### 6. Состояние: желаемое и наблюдаемое

Публикация — durable запись, а не только строка деплоя:

`id`, `env_id`, `version`, `generation`, `status`, `desired_state`,
`attempt`, `image_digest`, `container_id`, `host_port`, `health_url`,
`reason{code,message}`, `log_ref`, `deadline_at`, метки времени.

`desired_state` — чего хочет человек (`running` или `stopped`).
`status` — что видно по факту. Расхождение лечится сверкой, а не руками.

Контейнеры получают метки `rivet.managed=true`, `rivet.project`,
`rivet.environment`, `rivet.publication`, `rivet.version`, `rivet.generation`.
По ним runner находит свои контейнеры после перезапуска Docker и убирает
осиротевшие.

### 7. Восстановление после перезапуска

Docker:

- контейнер создаётся с `--restart unless-stopped` и без `--rm`: после
  перезапуска демона он поднимается сам, `container_id` сохраняется;
- сверка (тик оркестратора) читает фактические контейнеры по меткам и
  приводит `status` к наблюдаемому: `running`, `unhealthy` (healthcheck
  не отвечает), `failed` (контейнер в `exited` и попытки исчерпаны);
- если контейнер не поднялся, runner делает до трёх попыток запуска
  (паузы 5, 15, 30 с). Не помогло — `failed` с кодом `container_exited`,
  событие и эскалация как у обычного провала публикации;
- `desired_state=stopped` не воскрешается: у остановленной публикации
  restart policy `no`.

rivetd:

- строки `building|starting|verifying` с истёкшим `deadline_at` (дедлайн
  джобы плюс грейс watchdog'а) переводятся в `failed` с кодом `agent_lost`:
  вечной «сборки» в консоли не остаётся;
- `running` и `stopped` восстанавливаются сверкой с Docker, образы и
  контейнеры не пересобираются;
- повторная доставка результата идемпотентна: CAS-переходы отбрасывают
  чужой и устаревший `publication_id`.

### 8. Ошибки — коды и русский текст

| код | когда | что видно |
| --- | --- | --- |
| `config_invalid` | проверка конфигурации | 422, поле в тексте |
| `recipe_not_detected` | нет маркеров рецепта | какой файл добавить |
| `build_failed` | ненулевой код сборки | хвост лога сборки |
| `healthcheck_failed` | старт не уложился в `startup_timeout_s` | адрес и код ответа |
| `loopback_not_bound` | `HostIp` не loopback | какие привязки получены |
| `port_conflict` | свободный порт не нашёлся | диапазон |
| `docker_unavailable` | нет доступа к демону | время последней попытки |
| `container_exited` | контейнер упал после старта | код выхода и хвост логов |
| `image_missing` | образ поколения удалён | предложение `redeploy` |
| `timeout` | дедлайн джобы | этап |
| `agent_lost` | runner пропал между этапами | идентификатор runner'а |

Тексты пишутся по-русски и идут в `reason.message`, журнал и лог
публикации. Секретов в них нет: параметров с секретами у типа нет.

### 9. Права и журнал

Создание и правка окружения — администратор проекта (как сейчас).
`publish`, `redeploy`, `restart`, `stop` — участник проекта. Каждое
действие пишет событие `environment.publish` с версией, поколением и
инициатором; правка конфигурации — `environment.config`, как сейчас.

### 10. Что осознанно не решено

Открытые вопросы, которые надо закрыть до реализации:

- **Постоянный порт.** Нужен, если внешний инструмент привязан к номеру
  порта. Вариант: поле `port`, при нём redeploy идёт с коротким простоем
  (старый контейнер гасится перед стартом нового на том же порту).
- **Секреты приложения.** Сейчас `env` — только открытые значения. Нужен
  вид шифрованного секрета публикации, перешифровка в `rivetd -rotate-key`
  и запрет вывода значения в API.
- **Общие ресурсы.** Postgres/Redis для локальной публикации: поднимать
  рядом контейнером или требовать внешний адрес.
