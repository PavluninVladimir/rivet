# local-docker-publish — дельта спеки

## ADDED Requirements

### Requirement: Тип окружения local_docker

Система ДОЛЖНА поддерживать тип окружения публикации `local_docker` наряду
с `ssh`, `k8s`, `pipeline` и `gitops`. Конфигурация такого окружения
описывается моделью `LocalDockerEnvironmentConfig` в поле
`config.local_docker`; поля других типов (`deploy_cmd`, `verify_cmd`,
`verify_url`, `host`) в ней отсутствуют.

Модель:

| поле | тип | обязательное | правило |
| --- | --- | --- | --- |
| `container_port` | целое | да | 1–65535, порт приложения внутри контейнера |
| `health_path` | строка | нет | начинается с `/`, до 200 символов, по умолчанию `/` |
| `recipe` | строка | нет | `auto`, `go`, `node`, `static`; по умолчанию `auto` |
| `build_context` | строка | нет | относительный путь внутри репозитория, без `..`, по умолчанию `.` |
| `startup_timeout_s` | целое | нет | 10–600, по умолчанию 120 |
| `stop_timeout_s` | целое | нет | 1–120, по умолчанию 10 |
| `env` | объект | нет | до 64 пар, имя `[A-Za-z_][A-Za-z0-9_]*`, значение одной строкой до 4096 символов |

Поля `port` в модели нет: порт публикации выбирает платформа.

#### Scenario: Создание окружения local_docker
- **WHEN** администратор проекта присылает
  `POST /api/v1/projects/{id}/environments` с `exec_type: local_docker` и
  `config.local_docker.container_port: 8080`
- **THEN** окружение создаётся, ответ 201, конфигурация возвращается с
  заполненными умолчаниями (`health_path: "/"`, `recipe: "auto"`,
  `startup_timeout_s: 120`, `stop_timeout_s: 10`, `build_context: "."`)

#### Scenario: Неизвестное поле конфигурации
- **WHEN** в `config.local_docker` приходит поле `port` или `deploy_cmd`
- **THEN** ответ 422, текст `config.local_docker: неизвестное поле …`

### Requirement: Проверка конфигурации и разделение типов

Система ДОЛЖНА проверять `LocalDockerEnvironmentConfig` при создании и при
правке окружения и ДОЛЖНА отклонять конфигурацию другого типа.

Проверки: диапазоны и умолчания из модели, `build_context` существует в
рабочей копии версии публикации, в `env` нет имён с префиксом `RIVET_`
(заняты протоколом) и нет переводов строк в значениях.

#### Scenario: Порт вне диапазона
- **WHEN** `container_port` равен 0 или 70000
- **THEN** ответ 422 с текстом `config.local_docker.container_port: ожидается 1–65535`

#### Scenario: Поле чужого типа
- **WHEN** у окружения `exec_type: local_docker` в конфигурации задан `deploy_cmd`, `verify_cmd`, `verify_url` или `host`
- **THEN** ответ 422 с текстом `config.<поле>: локальная Docker-публикация не принимает ручные команды и адреса`

#### Scenario: local_docker в чужом типе
- **WHEN** у окружения `exec_type: ssh` задан `config.local_docker`
- **THEN** ответ 422 с текстом `config.local_docker: допустим только для exec_type local_docker`

#### Scenario: Зарезервированное имя переменной
- **WHEN** в `env` приходит имя `RIVET_ENV`
- **THEN** ответ 422 с текстом `config.local_docker.env: имя с префиксом RIVET_ зарезервировано`

### Requirement: Bind только на loopback

Система ДОЛЖНА публиковать контейнер исключительно на `127.0.0.1` или
`::1`. Порт выбирается платформой из свободных в диапазоне 20000–29999 на
хосте runner'а. Публикация на `0.0.0.0`, `::`, на адрес хоста в локальной
сети или в любой интерфейс вне loopback ЗАПРЕЩЕНА.

После запуска контейнера runner ДОЛЖЕН проверить через `docker inspect`, что
`HostIp` каждой опубликованной привязки — `127.0.0.1` или `::1`. Пустой
`HostIp` читается как `0.0.0.0` и считается нарушением. Нарушение ДОЛЖНО
немедленно остановить и удалить контейнер, а публикацию перевести в `failed`
с кодом `loopback_not_bound`.

Сетевые режимы `host`, `macvlan`, `ipvlan` и `container:<id>` ЗАПРЕЩЕНЫ:
loopback-привязки порта в них нет.

#### Scenario: Успешная публикация
- **WHEN** публикация версии проходит сборку и healthcheck
- **THEN** статус отдаёт `listen: "127.0.0.1:20123"`, а `docker inspect`
  показывает `HostIp: "127.0.0.1"`

#### Scenario: Демон Docker публикует на все адреса
- **WHEN** после запуска `HostIp` привязки пустой или равен `0.0.0.0`
- **THEN** контейнер останавливается и удаляется, публикация получает
  `failed` с кодом `loopback_not_bound` и текстом фактических привязок,
  конфигурация окружения не меняется

#### Scenario: Попытка выйти наружу через конфигурацию
- **WHEN** пользователь пытается указать адрес публикации, `host` или
  сетевой режим
- **THEN** таких полей в контракте нет, ответ 422 на неизвестное поле,
  публикация остаётся на loopback

### Requirement: Запрет ручных shell-команд

Система НЕ ДОЛЖНА исполнять команды, заданные пользователем, при
локальной Docker-публикации. Полей `deploy_cmd`, `verify_cmd`,
`monitor.check_cmd`, `monitor.logs_cmd` у `local_docker` нет, а их наличие
в запросе — ошибка 422.

Runner исполняет только фиксированный набор операций платформы: подготовка
рабочей копии версии, генерация Dockerfile по рецепту, `docker build`,
`docker run`, `docker stop`, `docker rm`, `docker inspect`, HTTP-проверка
healthcheck, чтение логов контейнера. Аргументы этих операций собираются
платформой; строки из конфигурации в них не подставляются, кроме значений
`env` (передаются списком `-e имя=значение` без shell).

#### Scenario: Команда в конфигурации
- **WHEN** в запросе на создание окружения приходит `deploy_cmd`
- **THEN** ответ 422, окружение не создаётся

#### Scenario: Команда наблюдения
- **WHEN** в `config.monitor` для `local_docker` приходит `check_cmd` или `logs_cmd`
- **THEN** ответ 422 с текстом `config.monitor.check_cmd: локальная публикация проверяется только URL`

### Requirement: Запрет ручных Dockerfile, nginx-конфигов и токенов

Пользователь НЕ ДОЛЖЕН быть обязан и НЕ ДОЛЖЕН иметь возможности задавать
Dockerfile, конфигурацию reverse proxy и токены для локальной публикации.

- Dockerfile генерирует платформа по рецепту во временном каталоге runner'а;
  файл в репозиторий не пишется, из конфигурации не принимается.
- Reverse proxy не нужен: приложение доступно по `listen` из статуса
  публикации. nginx-конфиг не принимается и не генерируется.
- Токены не нужны: образ не отправляется в registry, регистрация runner'а
  и git-токен для локальной публикации не запрашиваются. Публикация идёт
  на хосте runner'а, у которого уже есть доступ к репозиторию проекта.

#### Scenario: Репозиторий без Dockerfile
- **WHEN** в репозитории версии нет Dockerfile, но есть `go.mod`
- **THEN** публикация собирается по рецепту `go` и доходит до `running`

#### Scenario: Пользователь присылает Dockerfile
- **WHEN** в запросе конфигурации приходит поле `dockerfile`
- **THEN** ответ 422 с текстом `config.local_docker: неизвестное поле dockerfile`

#### Scenario: Публикация без registry и токена
- **WHEN** публикация выполняется на runner'е с capability `docker`
- **THEN** образ остаётся локальным, наружу не отправляется, токен
  registry не запрашивается

### Requirement: Рецепты сборки образа

Система ДОЛЖНА собирать образ по одному из фиксированных рецептов
платформы: `go`, `node`, `static`. При `recipe: auto` рецепт определяется
по маркерам рабочей копии версии в порядке `go.mod` → `package.json` →
`index.html` в корне `build_context`.

Базовые образы рецептов закреплены digest'ом. Аргументы сборки, `build-args`
и секреты в сборку не передаются. Нет ни одного маркера — провал с кодом
`recipe_not_detected` и текстом, какой файл добавить.

#### Scenario: Автоопределение Go
- **WHEN** в `build_context` есть `go.mod` и ровно один каталог `cmd/*`
- **THEN** собирается образ рецептом `go`, точка входа — этот каталог

#### Scenario: Маркеров нет
- **WHEN** в `build_context` нет ни `go.mod`, ни `package.json`, ни `index.html`
- **THEN** публикация получает `failed` с кодом `recipe_not_detected` и
  текстом «добавьте go.mod, package.json или index.html»

### Requirement: Публикация как объект с поколениями

Система ДОЛЖНА вести публикацию локального окружения как durable объект с
номером поколения. Поколение увеличивается на каждой успешной публикации.
У окружения ДОЛЖНА быть не больше одной активной публикации; повторный
запрос во время активной публикации получает 409.

`POST /api/v1/environments/{id}/publish` ставит публикацию HEAD базовой
ветки проекта. Для `exec_type: local_docker` существующий
`POST /api/v1/environments/{id}/deploy` — синоним `publish`.

#### Scenario: Публикация HEAD
- **WHEN** участник проекта вызывает `publish` у окружения без активной публикации
- **THEN** ответ 202 с публикацией в статусе `queued` и версией HEAD

#### Scenario: Вторая публикация во время первой
- **WHEN** публикация уже идёт и приходит второй `publish`
- **THEN** ответ 409 с кодом `publication_in_progress`

#### Scenario: Окружение на паузе
- **WHEN** автопубликации окружения на паузе и приходит `publish`
- **THEN** ответ 409 с кодом `environment_paused`, сначала нужен `resume`

### Requirement: Healthcheck публикации

Система ДОЛЖНА проверять готовность публикации с runner'а по адресу
`http://127.0.0.1:<port><health_path>`. Успех — код ответа 200–399.
Таймаут одного запроса 2 с, тело читается не больше 4 КиБ и не
сохраняется, redirect не отслеживается.

Стартовая проверка идёт до `startup_timeout_s`. Не уложилась — публикация
проваливается с кодом `healthcheck_failed`, новый контейнер удаляется.

Периодический контроль после публикации выполняется наблюдением окружения:
`monitor.check_url` платформа заполняет сама из `listen`, проверка идёт с
сети runner'а.

#### Scenario: Приложение поднялось
- **WHEN** контейнер отвечает 200 на `health_path` в пределах `startup_timeout_s`
- **THEN** публикация переходит в `running`, `health_url` содержит
  `http://127.0.0.1:<port><health_path>`

#### Scenario: Приложение не отвечает
- **WHEN** за `startup_timeout_s` не получен код 200–399
- **THEN** новый контейнер удаляется, публикация получает `failed` с кодом
  `healthcheck_failed` и последним кодом ответа в тексте

### Requirement: Состояния публикации и переходы

Система ДОЛЖНА вести состояния публикации: `queued`, `building`,
`starting`, `verifying`, `running`, `unhealthy`, `stopping`, `stopped`,
`failed`, `unknown`. Раздельно хранятся `desired_state` (`running` или
`stopped`) и наблюдаемый `status`.

Разрешённые переходы:

- `queued → building` — runner взял публикацию;
- `building → starting` — образ собран;
- `starting → verifying` — контейнер запущен и loopback-привязка подтверждена;
- `verifying → running` — healthcheck пройден;
- `building | starting | verifying → failed` — ошибка этапа;
- `running → stopping → stopped` — `stop`;
- `running → unhealthy` — периодическая проверка не отвечает;
- `unhealthy → running` — проверка снова отвечает;
- `running | unhealthy → failed` — контейнер упал и попытки исчерпаны;
- `failed → queued` — `publish` или `redeploy`;
- `unknown` — runner недоступен, факт неизвестен; из `unknown` публикацию
  выводит только сверка: в `running`, `unhealthy`, `stopped` или `failed`.

Переходы делаются CAS-ом по `publication_id` и `runner_id`; устаревший
результат отбрасывается и состояние не меняет.

#### Scenario: Успешный путь
- **WHEN** публикация проходит сборку, запуск и проверку
- **THEN** статус меняется `queued → building → starting → verifying → running`,
  каждое действие оставляет событие в журнале

#### Scenario: Устаревший результат runner'а
- **WHEN** приходит результат по `publication_id`, который уже финализирован
- **THEN** результат отбрасывается, статус не меняется

### Requirement: Обработка ошибок сборки и проверки

Провал на любом этапе ДОЛЖЕН завершать публикацию детерминированно:
финальный статус `failed`, код и русский текст в `reason`, хвост лога в
логе публикации, событие в журнале. Провал публикации ДОЛЖЕН ставить
автопубликации окружения на паузу и создавать эскалацию — как у провала
любого деплоя.

Работающая предыдущая версия при провале НЕ ДОЛЖНА останавливаться.

#### Scenario: Ошибка сборки
- **WHEN** сборка образа завершилась ненулевым кодом
- **THEN** публикация получает `failed` с кодом `build_failed`, старый
  контейнер продолжает работать, автопубликации на паузе

#### Scenario: Нет доступа к Docker
- **WHEN** runner не может обратиться к демону Docker
- **THEN** публикация получает `failed` с кодом `docker_unavailable`,
  сверка повторяет проверку и не держит вечный «building»

#### Scenario: Дедлайн джобы
- **WHEN** публикация не уложилась в дедлайн джобы и грейс watchdog'а
- **THEN** публикация получает `failed` с кодом `timeout` и этапом в тексте

### Requirement: Безопасный redeploy

`POST /api/v1/environments/{id}/redeploy` ДОЛЖЕН публиковать версию заново
без простоя работающей версии: новое поколение поднимается на свободном
loopback-порту, проходит healthcheck, и только после успеха старый
контейнер получает SIGTERM (SIGKILL через `stop_timeout_s`).

Провал нового поколения оставляет работать предыдущее; `status` и `listen`
остаются от него, а провал фиксируется в `reason` публикации.

Без параметров `redeploy` берёт версию последней успешной публикации.
Параметр `version` берёт версию из истории публикаций окружения; версии вне
истории — 422. Если успешной публикации ещё не было и `version` не передан —
409 с кодом `no_publication`. Одновременный `redeploy` при активной
публикации — 409.

Образы предыдущих поколений хранятся для отката: последние два, более
старые удаляются сверкой.

#### Scenario: Redeploy той же версии
- **WHEN** участник вызывает `redeploy` у работающего окружения
- **THEN** новое поколение поднимается на новом порту, старый контейнер
  останавливается после успешного healthcheck, простой не возникает

#### Scenario: Redeploy сломанной версии
- **WHEN** новая сборка или healthcheck провалились
- **THEN** работает прежнее поколение, `status: running`, `listen` не
  меняется, публикация получает `failed` с причиной

#### Scenario: Версия вне истории
- **WHEN** `redeploy` приходит с версией, которой нет в истории окружения
- **THEN** ответ 422 с текстом `version: нет в истории публикаций окружения`

### Requirement: Перезапуск и остановка

`POST /api/v1/environments/{id}/restart` ДОЛЖЕН перезапускать контейнер
текущего поколения без пересборки. Нет публикации или `desired_state:
stopped` — 409. Перезапуск во время активной публикации — 409 с кодом
`operation_in_progress`.

`POST /api/v1/environments/{id}/stop` ДОЛЖЕН останавливать контейнер:
SIGTERM, затем SIGKILL через `stop_timeout_s`, `desired_state: stopped`,
`status: stopped`. Повторный `stop` идемпотентен: ответ 200 без нового
события.

Остановленная публикация НЕ ДОЛЖНА подниматься сама: restart policy `no`,
сверка не воскрешает контейнер.

#### Scenario: Перезапуск
- **WHEN** участник вызывает `restart` у работающей публикации
- **THEN** контейнер перезапускается на том же порту и образе, статус
  возвращается в `running` после healthcheck

#### Scenario: Остановка
- **WHEN** участник вызывает `stop`
- **THEN** контейнер останавливается, `desired_state: stopped`,
  `status: stopped`, событие в журнале

#### Scenario: Повторная остановка
- **WHEN** `stop` вызван у уже остановленной публикации
- **THEN** ответ 200, состояние не меняется, событие не пишется

### Requirement: Логи публикации

`GET /api/v1/environments/{id}/publication/logs` ДОЛЖЕН отдавать логи
публикации текстом: `stream=builder` — лог сборки, `stream=container` —
лог контейнера текущего поколения, `tail` — число последних строк
(по умолчанию 200, максимум 5000). Логи хранятся ограниченно: не больше
2 МиБ на поток и не больше трёх последних поколений.

Логов нет — 404. Секретов в логах нет: параметров с секретами у типа нет.

#### Scenario: Лог сборки
- **WHEN** участник запрашивает `logs?stream=builder&tail=100`
- **THEN** ответ 200 `text/plain; charset=utf-8` с последними 100 строками

#### Scenario: Контейнера нет
- **WHEN** публикация остановлена и запрошен `stream=container`
- **THEN** ответ 404

### Requirement: Наблюдение окружения

Для `local_docker` наблюдение ДОЛЖНО проверять URL с сети runner'а:
`monitor.check_url` заполняется платформой из `listen` публикации и
пользователем не задаётся. `monitor.check_cmd` и `monitor.logs_cmd`
ЗАПРЕЩЕНЫ. Провал проверки переводит `status` в `unhealthy`, возврат
ответа — в `running`.

#### Scenario: Публикация перестала отвечать
- **WHEN** три проверки подряд не дали код 200–399
- **THEN** `status: unhealthy`, событие в журнале, контейнер не удаляется

#### Scenario: Проверка восстановилась
- **WHEN** очередная проверка дала 200–399
- **THEN** `status: running`

### Requirement: Сохранение состояния и сверка

Состояние публикации ДОЛЖНО храниться в БД и восстанавливаться после
перезапуска rivetd. Runner ДОЛЖЕН помечать контейнеры метками
`rivet.managed`, `rivet.project`, `rivet.environment`, `rivet.publication`,
`rivet.version`, `rivet.generation`; сверка ДОЛЖНА по этим меткам
приводить `status` к фактическому состоянию.

Контейнеры с метками `rivet.managed`, на которые не ссылается активная
публикация, ДОЛЖНЫ удаляться сверкой после грейса 10 минут. Удаление
окружения или проекта ДОЛЖНО удалять его контейнеры и образы.

#### Scenario: Перезапуск rivetd
- **WHEN** rivetd перезапустился во время публикации
- **THEN** публикации в `building|starting|verifying` с истёкшим дедлайном
  становятся `failed` с кодом `agent_lost`, а `running` и `stopped`
  восстанавливаются сверкой без пересборки

#### Scenario: Осиротевший контейнер
- **WHEN** сверка находит контейнер с метками rivet, которого нет среди
  активных публикаций, дольше 10 минут
- **THEN** контейнер останавливается и удаляется, событие в журнале

#### Scenario: Удаление окружения
- **WHEN** администратор удаляет окружение с публикацией
- **THEN** выполняющаяся публикация даёт 409, а после остановки контейнеры,
  образы и записи публикаций удаляются

### Requirement: Восстановление после перезапуска Docker

Контейнер публикации ДОЛЖЕН создаваться с `--restart unless-stopped`, без
`--rm`, чтобы после перезапуска демона Docker он поднимался сам.
Остановленная публикация (`desired_state: stopped`) ДОЛЖНА иметь restart
policy `no`.

После перезапуска демона сверка ДОЛЖНА: найти контейнер по меткам,
проверить привязку `127.0.0.1`/`::1`, выполнить healthcheck и привести
`status` к `running`. Контейнер в `exited` при `desired_state: running`
ДОЛЖЕН быть запущен заново, до трёх попыток с паузами 5, 15, 30 с.
Попытки исчерпаны — `failed` с кодом `container_exited`.

#### Scenario: Docker перезапустился
- **WHEN** демон Docker перезапущен, публикация была в `running`
- **THEN** контейнер поднимается, сверка возвращает `status: running` и тот
  же `listen`

#### Scenario: Контейнер не поднялся
- **WHEN** после трёх попыток контейнер не отвечает
- **THEN** `status: failed`, код `container_exited`, событие и эскалация

#### Scenario: Остановленную публикацию не воскрешаем
- **WHEN** демон Docker перезапущен, публикация была `stopped`
- **THEN** контейнер не запускается, `status: stopped`

### Requirement: API-контракт публикации

Система ДОЛЖНА предоставить операции `publish`, `redeploy`, `restart`,
`stop`, `status`, `logs` для окружения `local_docker` и отдавать статус
публикации полем `status` с `desired_state`, `generation`, `listen`,
`health_url`, `reason`. Полная форма запросов и ответов — в
`api-contract.md` этого change.

Права: `publish`, `redeploy`, `restart`, `stop` — участник проекта,
конфигурация окружения — администратор. Каждое действие пишет событие.

#### Scenario: Статус публикации
- **WHEN** участник запрашивает `GET /api/v1/environments/{id}/publication`
- **THEN** ответ 200 с публикацией и актуальным `listen`

#### Scenario: Чужой проект
- **WHEN** публикацию запрашивает не участник проекта окружения
- **THEN** ответ 404, существование окружения не раскрывается

### Requirement: Веб-консоль локальной публикации

rivet-web ДОЛЖЕН показывать карточку публикации: статус, версию,
поколение, `listen` с копированием, кнопки «Опубликовать», «Пересобрать»,
«Перезапустить», «Остановить», «Логи». Форма конфигурации содержит
`container_port`, `health_path`, `recipe`, `build_context`, `env`,
`startup_timeout_s`, `stop_timeout_s` и не содержит полей Dockerfile,
nginx, токенов и команд.

Ошибки показываются по-русски; 409 во время активной операции — «публикация
уже идёт», без дублирования кнопки.

#### Scenario: Провал сборки в консоли
- **WHEN** публикация провалилась с кодом `build_failed`
- **THEN** карточка показывает причину и ссылку на лог сборки, кнопка
  «Пересобрать» активна

#### Scenario: Публикация идёт
- **WHEN** открыт статус `building`
- **THEN** кнопки публикации неактивны, показан этап

### Requirement: Проверка на E2E-стенде

rivet-e2e ДОЛЖЕН покрыть локальную публикацию сценариями: успешная
публикация, loopback-only (в списке слушающих сокетов нет `0.0.0.0`),
безопасный redeploy без простоя, провал сборки с сохранением предыдущего
поколения, `restart` и `stop`, восстановление после перезапуска демона
Docker, запрет `deploy_cmd` и `monitor.check_cmd` ответом 422.

#### Scenario: Loopback-only на стенде
- **WHEN** публикация дошла до `running`
- **THEN** `docker inspect` показывает `HostIp` `127.0.0.1`, а `ss -ltn`
  не содержит порта публикации на `0.0.0.0`

#### Scenario: Провал сборки на стенде
- **WHEN** публикуется версия со сломанным `go.mod`
- **THEN** публикация `failed` с кодом `build_failed`, предыдущее поколение
  остаётся `running` и отвечает по своему `listen`
