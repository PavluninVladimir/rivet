## Контекст

Кода нет; требования зафиксированы в `define-rivet-requirements`. Ограничения, влияющие на выбор хранилищ: биллинг-метеринг обязан выводиться из event log идемпотентно (`backend/monetization`); event log — append-only и источник истины (`backend/observability`); переходы статусов атомарны и детерминированы (`backend/orchestration`); self-hosted-развёртывание бесплатного ядра должно быть простым (границы open-core); масштаб событий мал (десятки в секунду даже при 50 runner'ах), единственный объёмный поток — терминальный вывод сессий.

## Цели / Не-цели

**Цели:**

- Зафиксировать состав хранилищ MVP и правила «что где живёт».
- Минимизировать операционную сложность self-hosted-установки (меньше коробок в docker-compose).

**Не-цели:**

- Схемы таблиц, индексы, миграции — предмет реализации.
- Транспорт runner ↔ control plane и клиентские API — отдельная проработка (см. Открытые вопросы).
- Масштабирование под тысячи организаций (облачный мультитенант) — пересмотр при появлении нагрузки.
- Границы первой версии продукта (перенесено из `define-rivet-requirements`): роли и SSO (платный тир, после базовых учётных записей), Epic на несколько репозиториев, межэпиковые зависимости в DAG. Эти темы не проектируются в первой архитектуре; их появление потребует отдельных изменений.

## Решения

- **PostgreSQL — единая система записи** для управляющего состояния (projects, epics, tasks, DAG, runners, sessions, environments), event log (append-only таблица), очереди планировщика (`SELECT … FOR UPDATE SKIP LOCKED`) и usage-агрегатов (материализованные представления). Обоснование: смена статуса, запись события и назначение задачи — один локальный коммит; event log, которому можно верить для биллинга, невозможен при разнесении state и событий по разным системам (распределённая транзакция). Альтернативы: выделенный брокер очередей (Redis/NATS) — отвергнут как лишняя коробка без выгоды на нашем масштабе; отдельный event store (event sourcing как архитектура) — отвергнут: у нас лог дополняет state, а не порождает его.
- **Объектное хранилище (S3-совместимое, self-hosted — MinIO) для тяжёлых артефактов**: полные транскрипты сессий, терминальный вывод, диффы/артефакты попыток. В Postgres — только ссылки и метаданные. Обоснование: построчные логи в реляционных таблицах раздувают базу и убивают vacuum; живой поток идёт клиентам напрямую (кольцевой буфер в памяти control plane), в хранилище уезжает завершённый чанк.
- **Векторный поиск — pgvector в том же Postgres**, когда появится слой памяти проекта (не в MVP). Обоснование: объёмы — десятки тысяч векторов на портфель, а «найди похожее в этом проекте с учётом прав» — это join с метаданными, который в отдельном векторном движке превращается в синхронизацию двух систем. Отдельная векторная БД (Qdrant/Pinecone) отвергнута: масштаб не тот, а SaaS-вариант ломает self-hosted. Требование к схеме памяти: хранить рядом с вектором модель и версию эмбеддинга для переиндексации.
- **Никакого Redis/кэша в MVP** — данные крошечные и живые, кэшировать нечего; появление кэша требует обоснования нагрузкой.
- **Связь runner ↔ control plane: gRPC bidirectional stream, соединение всегда исходящее от runner'а.** Runner (наш Go-бинарник `rivet-runner`) устанавливает единственное долгоживущее соединение к control plane: вверх идут события, чанки транскрипта, usage и heartbeat; вниз — назначения задач, контекст и команды (пауза, отмена). Исходящее соединение решает NAT/VPN-случай (runner в закрытом периметре) без всякой настройки сети. Protobuf даёт типизированный, версионируемый протокол — это тот самый публичный контракт для SDK адаптеров. Альтернативы: WebSocket+JSON — проще отлаживать, но контракт слабее и версионирование ручное; long-poll — лишние задержки для live-стриминга. Переподключение: runner повторяет undelivered-события по своему локальному журналу (at-least-once, дедупликация по id события на стороне plane).
- **Клиентский API: HTTP/JSON + SSE, без gRPC для клиентов.** Web-консоли и мобильным приложениям — обычный REST (`/api/v1`) и Server-Sent Events для живых обновлений (переподключение с `Last-Event-ID` из коробки). gRPC-web отвергнут: тащит прокси-слой и усложняет отладку в браузере; у клиентов нет требований, которые не закрывает SSE.
- **Структура Go-репозитория: один модуль, три бинарника.** `cmd/rivetd` (control plane: API, планировщик, SCM, стриминг), `cmd/rivet-runner` (агент на машине исполнителя: gRPC-клиент + PTY-обёртка), `cmd/rivet` (CLI для dev-операций). Общий код в `internal/` (domain, store, orchestrator, scm, api, stream), публичный протокол в `pkg/protocol` (protobuf + Go SDK для сторонних адаптеров). Альтернатива «микросервисы со старта» отвергнута: один процесс `rivetd` с внутренними пакетами достаточен до реальной нагрузки и радикально проще для self-hosted.
- **Стартовая среда разработки** (решение владельца, 2026-08-09): первый SCM-адаптер — GitHub (dogfooding без VPN); control plane, Postgres+MinIO (docker compose) и первые runner'ы — на Mac разработчика; первый подопытный проект для полного цикла — сам Rivet (как только ядро способно провести задачу через конвейер, Rivet строит себя). GitLab self-hosted и распределённые runner'ы подключаются следом, сетевую модель протокола это не упрощает — протокол проектируется как сетевой с первого дня, просто первые соединения локальные.

## Риски / Компромиссы

- [Postgres становится единой точкой отказа] → на нашем масштабе приемлемо; стандартные бэкапы/реплика; распил начнётся только с реальной нагрузкой облака.
- [Терминальные логи потеряются при падении control plane до сброса чанка] → допустимо для live-буфера; завершённые этапы сбрасываются немедленно, event log не страдает (он в Postgres).
- [pgvector отстаёт от специализированных движков по фичам] → нам нужны knn+фильтры, не более; пересмотр при росте на порядки.
- [Обязательный Postgres усложняет «скачал и запустил» для соло] → осознанный компромисс ради одного код-пути; вопрос SQLite оставлен открытым до проверки спроса.

## Открытые вопросы

- Доставка секретов деплоя runner'ам, минуя control plane открытым текстом (перенесено из design `define-rivet-requirements`); не блокирует вертикальный срез — деплой в нём не участвует.
- Нужен ли SQLite-бэкенд для соло-сегмента «один бинарник» — вернуться после первых self-hosted-установок.
- Гранулярность партиционирования event log (по времени/проекту) — решается при реализации, когда появятся реальные объёмы.
