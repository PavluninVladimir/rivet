# backend/domain-model Specification

## Purpose

Определяет сущности Rivet — Project, Epic, Task, Runner — их атрибуты, DAG зависимостей и статусные модели с допустимыми переходами. Это словарь, на который опираются все остальные capabilities.

## Requirements

### Requirement: Иерархия Project → Epic → Task

Система ДОЛЖНА организовывать работу в иерархию: Project (продукт/репозиторий) содержит Epics, Epic содержит Tasks. Каждая задача принадлежит ровно одному Epic, каждый Epic — ровно одному Project. Epic привязан к репозиторию, в котором выполняется работа.

#### Scenario: Просмотр иерархии

- **WHEN** пользователь открывает Project
- **THEN** он видит список Epics проекта с их статусами и прогрессом, а внутри Epic — его задачи

### Requirement: Статусная модель задачи

Задача ДОЛЖНА находиться ровно в одном из статусов: `queued` (ждёт зависимости), `ready` (зависимости выполнены, ждёт runner), `running` (реализация), `testing` (автопроверки), `review` (независимая проверка), `fixing` (исправление замечаний), `blocked` (требуется решение человека), `failed` (исчерпаны попытки или невосстановимая ошибка), `done` (смержена), `cancelled` (отменена человеком, исключена из DAG). Переходы между статусами выполняет только оркестратор по детерминированным правилам; агент не меняет статус напрямую. Допустимые переходы:

| Из \ событие | Переход |
|---|---|
| `queued` | → `ready` (все зависимости done) · → `blocked` (зависимость failed/cancelled) · → `cancelled` |
| `ready` | → `running` (назначен runner) · → `queued` (правка плана добавила зависимость) · → `cancelled` |
| `running` | → `testing` (реализация завершена) · → `blocked` (вопрос человеку) · → `failed` (невосстановимая ошибка) · → `cancelled` |
| `testing` | → `review` (проверки прошли, PR создан) · → `fixing` (проверки упали) · → `failed` (исчерпан лимит) |
| `review` | → `done` (одобрено и смержено) · → `fixing` (замечания) · → `failed` (исчерпан лимит) |
| `fixing` | → `testing` (исправление готово) · → `blocked` (вопрос человеку) · → `failed` (исчерпан лимит) |
| `blocked` | → `queued`/`ready` (решение человека, возврат в планирование) · → `cancelled` |
| `failed` | → `queued`/`ready` (человек разрешил повтор) · → `cancelled` |
| `done`, `cancelled` | терминальные — переходов нет |

Матрица полна: каждый нетерминальный статус имеет выход, недостижимых статусов нет.

#### Scenario: Задача становится ready

- **WHEN** последняя из зависимостей задачи переходит в `done`
- **THEN** оркестратор переводит задачу из `queued` в `ready`

#### Scenario: Недопустимый переход отклоняется

- **WHEN** поступает событие, требующее перехода, не предусмотренного статусной моделью (например, `done` → `running`)
- **THEN** переход не выполняется, а в event log записывается ошибка

### Requirement: DAG зависимостей

Зависимости задач внутри Epic ДОЛЖНЫ образовывать ориентированный ациклический граф. Система ДОЛЖНА отклонять план или правку, создающую цикл, и УМЕТЬ вычислять критический путь Epic.

#### Scenario: Цикл отклоняется

- **WHEN** правка плана добавляет зависимость, создающую цикл (A → B → A)
- **THEN** правка отклоняется с указанием цикла

#### Scenario: Критический путь

- **WHEN** пользователь запрашивает критический путь Epic
- **THEN** система возвращает последовательность задач, определяющую минимальную длительность Epic

### Requirement: Статусная модель Epic

Epic ДОЛЖЕН находиться ровно в одном из статусов: `planned` (план построен, не запущен), `running` (выполняется), `paused` (приостановлен человеком), `done` (все задачи завершены), `archived` (убран из активных). Действия человека: запуск, пауза, возобновление, архивация.

#### Scenario: Завершение Epic

- **WHEN** последняя задача Epic переходит в `done` или `cancelled`
- **THEN** Epic переходит в `done`, и его можно архивировать

### Requirement: Атрибуты задачи

Задача ДОЛЖНА иметь: заголовок, описание, acceptance criteria (проверяемый список), список зависимостей, требуемые capabilities, оценку трудоёмкости (используется для взвешенного прогресса Epic и критического пути), лимит попыток и счётчик использованных попыток, а после запуска — назначенный runner, рабочую ветку (`agent/task-<N>`), связанный PR, длительность и израсходованные токены.

#### Scenario: Карточка задачи

- **WHEN** пользователь открывает задачу
- **THEN** он видит все перечисленные атрибуты, включая статус каждого acceptance criterion и счётчик попыток (например, «2 / 3»)

### Requirement: Пользователи и членство в проекте

Система ДОЛЖНА вести учётные записи пользователей и их членство в проектах. Субъект «human» в событиях и назначениях ДОЛЖЕН быть идентифицированным пользователем. Доступ к данным проекта (задачи, сессии, эскалации) имеют только его участники.

#### Scenario: Действие атрибутировано

- **WHEN** участник отвечает на эскалацию или запускает Epic
- **THEN** событие в event log содержит его идентичность, а не обезличенное «human»

### Requirement: Сессия как сущность

Сессия — единица работы агента — ДОЛЖНА иметь: водителя (пользователь или планировщик), тип агента и модель, проект, ветку/scope, способ подключения и глубину данных, транскрипт, метрики (длительность, токены). Задача оркестратора при выполнении порождает сессии (по одной на попытку); интерактивная сессия человека существует без задачи.

#### Scenario: Сессии попытки задачи

- **WHEN** пользователь открывает историю задачи с двумя попытками
- **THEN** он видит две связанные сессии с транскриптами и метриками каждой попытки

### Requirement: Окружения публикации в модели проекта

Проект ДОЛЖЕН содержать ноль или более окружений публикации (environment) с типом исполнения, правилом запуска и историей публикаций. Окружение принадлежит ровно одному проекту.

#### Scenario: История публикаций окружения

- **WHEN** пользователь открывает окружение проекта
- **THEN** он видит историю публикаций: версии, время, результат, кто/что инициировал

### Requirement: Статусная модель runner'а

Runner ДОЛЖЕН находиться ровно в одном из статусов: `idle` (свободен), `running` / `testing` / `review` (занят соответствующим этапом задачи), `offline` (потерял связь). Runner, не подтверждающий связь дольше порога, ДОЛЖЕН помечаться `offline` с указанием времени последнего контакта.

#### Scenario: Потеря связи

- **WHEN** runner не выходит на связь дольше установленного порога
- **THEN** он помечается `offline`, текущая попытка его задачи перезапускается с нуля через планирование (частичная работа остаётся в ветке задачи), а в event log пишется событие
